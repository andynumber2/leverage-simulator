<assumption_delta_decision>
## Does the identity model still name the right noun?

**Signal:** the deterministic scan fired a `pluralization` signal on the ROADMAP's "…alongside…"
phrasing. The phase introduces a **set** of named preset scenarios where the app previously had a
single implicit landing state.

**The noun that is now primary:** the run's parameter set, serialized as `PermalinkParams` by
`src/app/permalink.ts`. It was primary before this phase and it stays primary.

**Decision:** `no-change`.

**Rationale:** D-19 already answers this question and answers it in the direction that avoids a
second identity. A preset stores a parameter set, never a URL string, and is applied by writing
through the same validated setters any parameter control uses. A preset is therefore a *named
producer* of the existing primary noun, not a new addressable unit competing with it. Promoting
"preset" to primary would mean minting a preset identifier that could appear in a link, which is
exactly the two-representations-of-every-preset failure D-19 rejected when it declined to emit
permalink strings at build time. Adding a preset id alongside the existing parameter state would be
the accepted-debt variant, and it buys nothing: after applying a preset, Copy link already produces
a correct, complete, self-contained permalink for it.

**Contract test encoding the generalized intent** (adopted, not merely suggested): every named
preset round-trips through the same `encodeParams`/`decodeParams` path as a hand-built run, for
every preset. That assertion lives in `tests/app/presets.test.ts`, Task 3, and it is the mechanical
statement that a preset is nothing more than a parameter set with a name.

This checkpoint is advisory. It records; it does not block.
</assumption_delta_decision>
