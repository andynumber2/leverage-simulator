<objective>
Put the data's provenance permanently on screen, generated from the manifest rather than
hand-authored (CRED-01), inside the region a user screenshots.

**User story (MVP):** **As a** skeptic handed a screenshot of a backtest, **I want to** see which
history tier it used, over what dates, from which sources, and which data seams the run crossed,
**so that** I can judge the data without asking the person who pasted it.

Purpose: PITFALLS G2 — unlabeled provenance. PROJECT.md rules out the footnote position by name.
Output: `provenance-fields.ts` (the traceable string builder), `ProvenanceStrip.tsx`, and the
build-failing traceability test.
</objective>

  <behavior>
    - Given a manifest series and a run window, the builder returns an ordered list of field records; each record carries a label, a rendered value and the manifest path the value came from.
    - Every returned record's manifest path resolves to a value present in the manifest object, and the record's rendered value contains that manifest value as a substring.
    - A run window that crosses no seams produces no seam record at all, rather than a record whose value is a zero count.
    - A run window that crosses exactly one seam produces singular copy; two or more produce plural copy.
    - A seam whose `lastDate` equals the window's `firstDate`, and a seam whose `firstDate` equals the window's `lastDate`, are both reported as crossed.
    - Crossed seams are ordered by ascending `firstDate`; two seams with the same `firstDate` keep their manifest array order across repeated calls.
    - No returned record's value contains any `license` or `termsUrl` string from the manifest's `sources[]` entries.
  </behavior>
  <action>
    Create `src/app/components/ResultColumn/provenance-fields.ts` exporting
    `ProvenanceField` (fields: `id`, `label`, `value`, `manifestPath`, and for the sources field the
    per-source `href` values) and
    `buildProvenanceFields(manifest, seriesId, window, tier, bundleVersion): ProvenanceField[]`,
    plus `crossedSeams(seams, window): SeamRecord[]`.

    `manifestPath` is a dotted path string naming exactly where the value came from, for example the
    path to the selected series' `firstDate` or to a given source's `source` name. This field exists
    so Task 3's traceability test can resolve the path against the real manifest object and prove
    the rendered string is not hand-authored prose. Every field record must carry one; a field with
    no manifest origin must not be constructible.

    Fields, in the Copywriting Contract's order: tier, date range, sources, seams-crossed (omitted
    entirely when empty), bundle version. Use the Contract's exact label and value templates,
    including the singular and plural seam forms.

    `crossedSeams` implements D-14: only the seams the active run window actually crosses render
    at all times, with the remainder one click away. It is an inclusive interval-overlap filter: a seam is crossed when its `firstDate`
    is less than or equal to the window's `lastDate` AND its `lastDate` is greater than or equal to
    the window's `firstDate`. Sort the result by ascending `firstDate` using a stable sort so equal
    keys keep manifest array order.

    The sources field renders each source's `source` name and carries its `url` as an href. It must
    never read, render or return the `license` or `termsUrl` fields, per D-15: redistribution terms
    are a fact about the project, not a caveat about the number, and rendering them in the result
    region invites reading them as a data-quality warning.

    The module contains no JSX and imports nothing from `solid-js`, so it is testable in the Node
    unit project.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Bundled manifest `sources[].url` -> DOM anchor href | A build-time-authored URL is placed into an href attribute. |
| Manifest field values -> rendered credibility claim | The strip's whole purpose is that its strings are the data's, not the author's. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-08 | Tampering | `ProvenanceStrip` source anchors | medium | mitigate | Render a source anchor only when its `url` begins with `http://` or `https://`; render the source name as plain text otherwise. The manifest is build-time-controlled and committed, so this is defence in depth against a future data-source addition, not a live exploit path. |
| T-05-09 | Repudiation | Hand-authored provenance drift | medium | mitigate | Task 3's traceability test resolves every rendered string's `manifestPath` against the real manifest and fails the build on a mismatch, so a later well-meant prose edit cannot go stale silently. |
| T-05-10 | Information Disclosure | Licence/terms text in the result region | low | mitigate | `provenance-fields.ts` never reads `license` or `termsUrl`, asserted by a grep acceptance criterion and by a test asserting no rendered value contains those strings. |
| T-05-SC | Tampering | npm installs | low | accept | No package-manager install in this plan. |
</threat_model>
