## Resolved before execution: how the bands are built without a dependency

`06-UI-SPEC.md`'s Registry Safety binds the whole phase, so `d3-contour` and `marchingsquares` are
both out. `06-RESEARCH.md`'s Don't Hand-Roll section is right that hand-rolling filled iso-BANDS
with polygon stitching and level-set management is error-prone geometry code. This plan sidesteps
that entirely by never building band polygons:

- **Filled bands** come from per-pixel evaluation, not geometry. Bilinearly resample the 200 by 50
  value field onto the display canvas, quantise each display pixel's interpolated value into a
  band, colour it with `valueToColor` at the band centre, and write the whole canvas in one
  `putImageData`. At 800 by 200 that is 160,000 pixel evaluations, which is cheap, and the band
  edges come out smooth and curved because the underlying resample is smooth. No polygons, no
  stitching, no self-intersection.
- **Iso-lines** come from marching squares emitting UNSTITCHED segments. Per grid cell, classify
  the four corners against the level, linearly interpolate the crossing point on each straddled
  edge, and emit the one or two segments the case table gives. Stroked segments render identically
  to a stitched polyline, so the stitching step that makes marching squares genuinely hard is not
  needed for an annotation layer. Saddle cases resolve by comparing the level against the mean of
  the four corners, which is the standard disambiguation and is a two-line rule.

That is the whole geometry surface: roughly sixty lines with no dependency, and both halves are
unit-testable against analytic fields.

`field-sampler.ts` exports `BAND_LEVELS`, `bandIndexFor(value)`, `resampleField(...)` and the
`CategoricalMask` type. `BAND_LEVELS` are the band boundaries in ramp-position space: eleven
evenly spaced boundaries across `[0, 1]`, giving ten bands, plus an explicit boundary at exactly
`rampPositionFor(1.0)` which is `0.5`, so the breakeven boundary is always a band edge rather than
falling inside a band. That is what makes the filled-contour form show breakeven as a SHAPE, which
is the entire premise of D-02 form 2 and of PITFALLS E1's complaint about a hidden threshold.
`bandIndexFor` maps a value to a band by its ramp position with the upper-band tie rule.

`resampleField(fixture, metric, geometry)` returns a `Uint8ClampedArray` RGBA buffer at the
display geometry plus nothing else: it performs the bilinear interpolation, the categorical
override, the band quantisation and the `valueToColor` lookup in one pass. Colour each band at its
CENTRE ramp position, not at its edge, so a band's colour is representative of the band rather than
of its boundary. For the categorical override, compute the four cells of the bilinear stencil
first; if any carries `CELL_FLAG_RUINED` or `CELL_FLAG_INCOMPLETE`, take the flag of the nearest
stencil cell by Euclidean distance in grid space and return that categorical colour with no
interpolation at all. Ties in distance break toward the lower row then the lower column, so the
rule is total.

Cache the `valueToColor` result per band index in a small array before the pixel loop rather than
calling it 160,000 times, so the per-pixel work is an array index. Preallocate the RGBA buffer once
per geometry and reuse it across calls, following the allocation discipline
`bench/canvas-grid.ts`'s `getPutImageDataBuffer` already established.

Write both unit test files in the `unit` project against analytic fields, in the style
