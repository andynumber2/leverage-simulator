## Recorded decision: the `runSweep(params)` interface seam is deferred to Phase 3

`01-RESEARCH.md` open question 2 left this unresolved and CONTEXT.md lists it under Claude's Discretion. It is resolved here explicitly rather than left implicit.

**Decision:** Phase 1 does NOT establish the permanent `runSweep(params)` interface seam recommended in `.claude/CLAUDE.md` section Q1. The sweep entry point created by this plan is named `runSpikeSweep` and is bench-internal.

**Reason:** phase criterion 1 calls this benchmark throwaway, and a permanent public contract designed against a spike's needs is a contract designed against the wrong requirements. Phase 3 owns the real kernel and should design the seam against the real parameter surface (arbitrary fractional leverage, contribution frequencies, dividend toggle, holding modes, user-supplied cost parameters) rather than against the six-field spike stand-in. The deliberately different name makes it impossible for a later phase to import the spike function believing it is the production seam.

**What Phase 1 does leave behind:** the bench arms in `bench/` remain as permanent, gated, `spike-synthetic`-sourced rows, because a figure that stops being measured the moment the phase ends cannot catch a regression, and PERF-11 requires measurement from the first executable phase onward. When Phase 3 lands the real kernel and Phase 7 lands the real sweep, they re-register PERF-02 and PERF-03 with source `production` and the spike arms are retired. The Rust crate is the only thing deleted at phase end, per D-13.

<objective>

Purpose: PERF-03 is the figure that decides plain JS versus WASM, and the whole reason the phase exists is that this number is currently an estimate.

</objective>

Use a small deterministic pseudo-random generator written inline (a counter-based or xorshift-style integer generator plus a Box-Muller or inverse-normal transform) rather than `Math.random`, so the series is byte-identical across machines, across runs, and across the JS and Rust arms. `bench/kernel.ts` exports `SWEEP_COLS` set to `200`, `SWEEP_ROWS` set to `50` (200 times 50 is the 10,000 cells PERF-03 names), the `SpikeKernelParams` interface carrying `leverage`, `entryIndex`, `initialInvestment`, `contributionAmount`, `contributionIntervalBars`, `financingSpread` and `expenseRatio`, the `SpikeKernelResult` interface, and `runSpikeBacktest(params, series, out)`.

`runSpikeBacktest` implements the real per-bar recurrence including the branchy parts, per D-12. Per bar: apply leverage to that bar's daily return and compound it into the running value, never to a cumulative return (PITFALLS A1); subtract financing on the borrowed portion computed as leverage minus one, times the short rate plus the financing spread, times `calendarDaysElapsed` divided by 365, so weekends and holidays are charged (PITFALLS A8); subtract the expense-ratio accrual on the flat trading-day convention, which is a genuinely different accrual basis from financing and must not be conflated with it (PITFALLS A4); add a contribution when the bar index is on the contribution interval; and clamp to exactly 0 with the ruin flag set the instant the computed value would reach or cross zero, after which every subsequent bar stays at exactly 0 and no contribution resurrects the position (PITFALLS A7). Document the day-count convention chosen for financing in a header comment.

Keep the hot loop allocation-free and monomorphic per PITFALLS F1 and F2: every accumulator is a preallocated `Float64Array` supplied by the caller, the ruin flag lives in a separate `Uint8Array` rather than as a sentinel mixed into the value array, and no object, array or boxed value is created inside the per-bar loop.

`bench/sweep.worker.ts` is a real module Worker. It imports `runSpikeBacktest` from `bench/kernel.ts` and `makeSeededGbmSeries` from `bench/synthetic-data.ts` so there is exactly one recurrence implementation in the phase, and exposes a `runChunk` function through `Comlink.expose`. `runChunk` receives the chunk's cell index range and a result `ArrayBuffer`, computes each cell in the range by running one full backtest over the 25,000-bar series, writes the per-cell summary value into a `Float64Array` view of that buffer, and returns the buffer.

`bench/sweep-pool.ts` exports `resolveWorkerCount()` and `runSpikeSweep(seed, options)` implementing D-10. Construct real Workers with `new Worker(new URL('./sweep.worker.ts', import.meta.url), { type: 'module' })`, one per `resolveWorkerCount()`, and wrap each with `Comlink.wrap`. Partition the 10,000 cells into chunks and dispatch them across the pool. Do not dispatch all 10,000 cells as one unit to one worker, per PITFALLS F4: chunk them so partition granularity is a real, measurable part of the figure. Pass each chunk's result buffer with `Comlink.transfer(buffer, [buffer])` so ownership moves rather than the buffer being structured-cloned, per PITFALLS F3 and the RESEARCH.md anti-pattern note; a copy stall folded into the measured figure would make this phase lock a budget against a cost the production implementation may not have. Choose the chunk count so each worker receives several chunks rather than exactly one, which keeps a slow worker from stranding the tail of the sweep; record the chosen chunk count and the reasoning in the plan SUMMARY, since sweep partitioning granularity is explicitly Claude's discretion in CONTEXT.md.

Time the wall clock from the `runSpikeSweep` call to the promise resolving with the final cell present, which is exactly what PERF-03 specifies as "wall-clock from user action to final cell". Include worker construction inside the timed region on the first repeat and state in the SUMMARY whether workers are reused across repeats, because worker startup is one of the costs research hand-waved and D-10 exists to surface it.
