<objective>
Make the sweep feel instant and make it cancellable, without ever showing the user a partially
computed field.

Purpose: PERF-04 says the user never faces a blank pane with a spinner, and PERF-06 says a
superseded sweep's results are discarded rather than painted. Under form 2 both are harder than they
sound: "cells appear as workers finish" is not directly renderable, because marching squares needs a
complete field to produce sensible boundary curves. D-12 resolves it by sweeping a strided subsample
first and painting a complete low-resolution contour, then refining.
Output: coarse-to-fine progressive paint, generation-token cancellation, and measured PERF-04 and
PERF-06 figures.
</objective>

  <behavior>
    - `isStaleGeneration(resultGeneration, currentGeneration)` is true exactly when the result's generation is lower than the current one, and false when equal.
    - A chunk result carrying a stale generation, fed directly into the merge path, leaves every cell of the live grid unchanged, including cells the stale chunk covered.
    - A chunk result carrying the current generation merges normally.
    - Starting a new sweep while one is in flight bumps the generation, returns synchronously without awaiting any in-flight worker call, and constructs no new Worker.
    - In-flight calls for the stale generation are allowed to settle; their results are dropped on arrival and their rejection, if any, does not surface as an unhandled rejection.
    - The pool survives an unbounded number of cancel-and-restart cycles with a constant worker count, asserted by driving 50 consecutive generation bumps and checking the worker count is unchanged.
    - A chunk that times out or whose worker fails marks its cells with `CELL_FLAG_INCOMPLETE` and increments a failed-cell count, rather than rejecting the whole sweep.
  </behavior>
  <action>
Add the generation layer to the persistent pool. Every `SweepChunkRequest` already carries
`generation` from plan 07-01; this task makes it load-bearing. Export `SweepRunHandle` (the object a
sweep start returns, carrying its generation and a way to observe completion) and
`isStaleGeneration`.

Structure the merge path so the generation comparison is the ONLY thing standing between an arriving
chunk and the live grid, and so that comparison is testable without a browser: put it in a pure
function that takes the arriving chunk, its generation, the current generation and the target grid,
and returns whether it merged. `tests/sweep/cancellation.test.ts` calls that function directly in the
fast Node `unit` project, which is what makes PERF-06's correctness separable from its timing (the
second `07-VALIDATION.md` Wave 0 requirement).

Do not tear down the pool. `bench/sweep-pool.ts`'s `finally { for (const worker of workers)
worker.terminate() }` is deliberately excluded: worker construction cost is real (Phase 1's own
measurement discipline includes it in every PERF-03 repeat) and D-32 requires cancelling on every
holding-period drag frame, so a teardown-and-reconstruct cancellation would spend the whole 16ms
PERF-06 budget on pool churn. Keep `watchWorkerFailure` attached before any dispatch, keep the
per-chunk timeout, and add a disposal path used only when sweep mode is left entirely.

Chunk failure is not sweep failure. A timed-out or failed chunk marks its own cells
`CELL_FLAG_INCOMPLETE` (the same flat neutral grey already reserved for a cell that carries no value,
so no third grey-adjacent state is invented) and increments a failed-cell counter the store exposes.
The rest of the sweep completes.

Keep the module header's stated plan, decision IDs and reasoning convention. No em dash characters.
Minimize ternaries and never nest them.

  </read_first>
  <action>
Split every sweep into two passes over the same persistent pool and the same generation.

**Coarse pass (D-12).** Sweep a strided subsample and build a COMPLETE low-resolution grid of its
own dimensions: every 4th entry-date column plus the last column, and every 4th leverage row plus the
last row, giving a 51 by 14 field of 714 cells, roughly one-fourteenth of the full grid and
comfortably inside PERF-04's 100ms. Including both axis endpoints matters: marching squares needs the
field's own extremes, and a coarse field that stops one column short of the domain edge produces a
boundary curve that moves when the full pass lands. The exact stride is Claude's Discretion under
`07-CONTEXT.md` provided the pass lands inside 100ms and paints a complete field; declare the two
strides as named constants so the figure can be re-tuned against a measurement rather than guessed
again.

Paint the coarse grid through the same `paintSweepField` the full grid uses. This is the same form at
a lower resolution, not a different chart: a two-stage form swap would read as a glitch, and a flat
fill during the sweep would hide the traceable boundary the form exists for.

**Full pass.** Refine to the full 200 by 50 grid over the remaining chunks, painting as chunks land.
The full grid replaces the coarse one whole when it is complete.

**No flash on cancellation (D-13).** When a new sweep starts, the previous COMPLETE field stays on
screen. Superseded results are discarded and never painted, and the new sweep's coarse pass replaces
the old field whole. There is never a half-old and half-new blended field and never an empty canvas.
The staleness window this creates is bounded by the coarse pass's own 100ms, which is why D-14 judges
it too short to warrant an affordance.

**No progress affordance (D-14).** No spinner, no bar, no percentage, no live cell count anywhere in
sweep mode. The field's own coarse-to-sharp refinement is the feedback. This is what PERF-04's "never
a blank pane with a spinner" asks for and it keeps one fewer element competing with the legend, the
axis labels and the caption strip.

**Live re-sweep on drag (D-32).** Dragging the holding-period control starts a sweep per drag
position, cancelling the prior one. Do not debounce (a constant to tune, and the picture lags the
control in a way that reads as lag) and do not commit on release (which would leave the cancellation
path unexercised in the one interaction that would exercise it). `scheduleSweep`'s existing
requestAnimationFrame coalescing is the only rate limiting.

**Store surface.** Extend `src/app/state.ts` with the remaining sweep signals this phase needs, so
later plans read them rather than adding parallel state: `sweepGeneration`, `coarseSweepGrid`,
`sweepFailedCellCount`, `displayedMetric` and `setDisplayedMetric` (seeded to the
multiple-of-contributed default), and `crosshairCell` and `setCrosshairCell`. Every one of them reads
or writes the SAME `BacktestRequest` fields the single-run path already owns wherever a field already
exists; do not introduce a parallel request shape. Plans 07-06, 07-07 and 07-08 consume these
signals; this plan defines them.
  </action>
