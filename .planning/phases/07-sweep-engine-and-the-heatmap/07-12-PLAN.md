  <context>
The zero-contribution sweep, which is the app's default view and the configuration PERF-03's
headline figure describes, is inside budget. The overrun is specific to the branch D-24 requires
when a contribution schedule is set: the annualized metric routes through `solveIrr` over
`buildCashFlows` instead of the closed-form `solveCagr`, and on the extended-tier entry-date axis
the earliest columns carry roughly 1,176 cash flows each.

The measured figures are in `07-PERF-03-BASELINE.md` sections 2 and 3. Read them there rather than
from this block, and quote them from there. Two things about them constrain how much weight they
carry: the contribution-schedule arm is `sampleCount=1`, disclosed as such and not a minimum-of-N
figure, and WINDOWS.md entry 2 plus the bench run's own measurement-band info line put roughly
plus-or-minus 13 percent (two standard deviations) on any single normalized figure. A 3x overrun
survives that band comfortably; a marginal one would not.

What is already ruled out, and why, so no option below re-litigates it:

- **Relaxing the budget.** PERF-01a, D-19 and 07-03-PLAN.md's own prohibition all forbid it. Not an
  option.
- **Retuning `NOMINAL_REFERENCE_MS`.** Budget-denominating under PERF-01a; its only effect would be
  to un-trip an escalation. Not an option.
- **Dropping IRR from the sweep, or refusing contribution schedules in sweep mode.** D-24 requires
  the sweep to mirror METR-01 and METR-02 exactly, because a CAGR field beside a single-run view
  that suppresses CAGR would make the app contradict itself on the same data. Not an option.
- **WASM.** D-20 listed it as a lever; Phase 1 spent it. 01-04 measured Rust at roughly 1.20x
  slower than JS on this recurrence, so adopting it makes PERF-03 worse.

Undo cost, for weighting: this is a recorded decision, not a code change, and the PROJECT.md row is
what later phases and later readers will treat as settled. A row that names a lever commits Phase 8
or a later phase to spending it; a row that accepts with a headroom plan commits whoever next
touches the sweep path to measuring against it. Either way, replacing the row later means writing a
superseding row and explaining why, the same way the SUPERSEDED (D-28) rows in that table do. That
is why this pause exists before the row is written.
  </context>
