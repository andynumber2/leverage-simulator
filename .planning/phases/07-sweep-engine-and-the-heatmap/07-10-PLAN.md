Let the reader magnify a region of the field without re-computing anything, and prove the gesture
holds a frame at full cell count.

Purpose: PERF-09 names pan and zoom explicitly, so dropping them would need a requirement change
rather than a design choice. D-34 rules out the more useful alternative (zoom that re-sweeps a
narrowed range at full resolution) because every step would be a roughly 800ms sweep, directly
contradicting the 60fps this requirement asks for.
Output: a viewport transform, rescaled axes that keep stating real values, and a measured PERF-09
figure.
</objective>

  <behavior>
    - `clampViewport` pins the pan offset to zero whenever the scale is at or below the fit scale, so panning a fit-scale field does nothing.
    - Above fit scale, the pan offset is clamped so the visible rectangle never extends past the field's own bounds in either axis.
    - `applyViewportTransform` at scale exactly 1.0 with zero offset is the identity transform, so the rendered field is pixel-identical to the un-zoomed field.
    - A zoom-out request at `ZOOM_MIN_SCALE` and a zoom-in request at `ZOOM_MAX_SCALE` each return the unchanged viewport rather than throwing or producing an out-of-range scale.
    - `visibleDomainFor(viewport, grid)` returns the first and last entry-date column index and the first and last leverage row index currently visible, derived from the transformed domain rather than from rounded display pixels, so the axis labels a caller draws from it always name real dates and real leverages.
    - Zooming toward a pointer position keeps the grid cell under that pointer fixed, asserted at three separate pointer positions.
  </behavior>
  <action>
Create `src/heatmap/viewport.ts` as pure transform maths with no DOM and no Solid import, following
the same zero-import discipline as its sibling modules so it runs in the fast Node `unit` project.
Export `SweepViewport` (a scale plus an x and y pan offset in field-rectangle space), `ZOOM_MIN_SCALE`
of 1.0, `ZOOM_MAX_SCALE` of 8.0, `clampViewport`, `applyViewportTransform` and `visibleDomainFor`.

The maximum of 8.0 is a planner-authored value: at 8x a 200-column entry-date axis shows 25 columns
and a 50-row leverage axis shows about 6 rows, which is well past the point where individual cells
are pointable, and going further would magnify past any useful reading of the field. No source
artifact fixes it; state it as a named constant with that reasoning in the module header.

The transform composes with the vertical flip that `resampleField` and `crosshairCellFor` already
apply. Do not re-derive the flip here: take the field rectangle and the flip as given and express the
viewport purely as a scale-and-translate on top, so there is exactly one place in the codebase that
knows row 0 paints at the bottom.

`visibleDomainFor` is what keeps D-34's "the axes rescale so they keep stating real dates and
leverages" honest. Derive the visible index range from the transformed domain and let the caller pick
ticks from `grid.meta.entryDates` and `integerLeverageTicks` within that range, so a tick always names
a value that exists rather than an interpolated display coordinate.

Create `tests/heatmap/viewport.test.ts` covering every behavior above in the fast Node project.
No em dash characters. Minimize ternaries and never nest them.
