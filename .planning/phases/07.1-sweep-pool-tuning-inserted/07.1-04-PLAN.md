<objective>
Produce the interactivity evidence that a worker-count change needs, decide the change against it,
and leave the correctness gates asserted against whatever partition shape results.

`workerCountForCores` returns `cores - 1`. On the declared 4-core baseline that is 3 workers, and
07.1-RESEARCH.md's reading of the profile is that "pool tuning", as PROJECT.md names the lever, will
mostly cash out as this one constant: transfer discipline is already zero-copy in both directions,
per-column resolution already happens once per column, and the PERF-03 bench's own entry-date axis
is near-uniform by design (every column within 99.15% of the longest), so chunk-shape rebalancing
has little headroom against the number that must move.

But `cores - 1` is not an arbitrary choice. It exists so the main thread stays free to paint and
respond while a sweep is in flight, which is PERF-04's, PERF-06's and PERF-07's contract. And no
bench in this project has ever run an interaction concurrently with an in-flight sweep, at any
worker count: `bench/perf-07.bench.test.ts` drags a slider with no sweep running, and
`bench/sweep-progressive.bench.test.ts` runs sweeps with no interaction. There is currently no
evidence either way. 07.1-RESEARCH.md's Pitfall 3 states the two legitimate paths plainly: build the
evidence, or keep the rule and treat any width-4 win as unavailable. Silently picking the first
path's conclusion without doing the work is not one of them.

This plan does the work first and decides second.

**On moving cost rather than eliminating it.** A fourth worker adds one more module evaluation and
one more `loadBundleFromFetch` decode per session. `bench/sweep.bench.test.ts` constructs its pool
in `beforeAll`, outside every timed repeat, and that exclusion is correct: production's
`getSweepPool` is a lazily-constructed module singleton that also builds once per session and is
reused for every sweep after. So the exclusion matches what a real user pays, and adding a worker
does not change that structure. What it does change is the size of that one-time cost, and the bench
never sees it. This plan discloses it rather than hiding it: the contention arm reports
cold-versus-warm first-sweep figures at both widths, so the added once-per-session cost sits on the
record beside the throughput gain.

Purpose: replace an untested safety margin with a measured one, in whichever direction the
measurement points.
Output: a contention bench arm, a recorded decision, and correctness gates that describe the shipped
partition shape.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| main thread to sweep Worker | `SweepChunkRequest` crosses `postMessage`. Internal, fully typed, never user-supplied. A width change alters how many of these boundaries exist, not what crosses them. |
| sweep compute to main-thread interactivity | The shared CPU. This is the boundary the `cores - 1` rule exists to protect and the one this plan measures for the first time. |
| measured pool width to deployed pool width | Two separate `workerCountForCores` declarations. A divergence here makes every PERF-03 figure describe something production does not run. |
