# Phase 07.1 Plan 04: Sweep Contention Evidence and Worker-Count Decision Summary

Built the first automated evidence in this project about main-thread responsiveness during a
real concurrent sweep, at `workerCount=3` and `workerCount=4`, and deferred the worker-count
adoption decision to plan 07.1-06's 4-core CI baseline against an explicit, pre-stated
threshold, because this sandbox's spare CPU capacity cannot stand in for the baseline's.

## Task 1: `bench/sweep-contention.bench.test.ts`

Created an informational-only bench arm (`commands.recordInfoLine` only, never
`commands.recordMeasurement`) that, for each of `BASELINE_WORKER_COUNT` (3) and
`BASELINE_WORKER_COUNT + 1` (4), in a fresh pool:

1. Measures a small (1x1), grid-size-independent cold sweep to isolate the added worker's
   one-time module-evaluation + bundle-fetch cost (`coldFirstSweepMs`).
2. Measures a full 200x50 warm sweep, unloaded (`warmSweepMs`).
3. Starts a second full 200x50 sweep and holds its promise while a `requestAnimationFrame`-driven
   loop repeatedly times one real `runBacktest` call over a real `resolveColumnSeries` result (the
   same kernel call `src/app/state.ts`'s `scheduleRun` performs per coalesced recompute) and the
   wall-clock gap since the previous frame callback -- stopping when the sweep's own promise
   resolves.

Emits one info line per width (`sweep-contention-width-3`, `sweep-contention-width-4`) plus one
comparison line (`sweep-contention-comparison`) naming the deltas. Fails loudly if fewer than 11
frames complete during the in-flight sweep, so no reported max/median rests on a single-sample
artifact (did not trigger: both widths completed 20+ frames in every observed run).

**Width is parameterized explicitly, not read from `workerCountForCores`.** The two widths
measured are `BASELINE_WORKER_COUNT` and `BASELINE_WORKER_COUNT + 1`, both passed directly as
`createSweepPool({ workerCount })`'s option. `BASELINE_WORKER_COUNT` is itself pinned to
`workerCountForCores(PERF_03_BASELINE_HARDWARE_CONCURRENCY)` (= 3), a compile-time constant, not
a host-following value (`resolveWorkerCount()`/`navigator.hardwareConcurrency` is never called
anywhere in this file). This means a single CI run at `hardwareConcurrency=4` -- or any host --
always yields both the width-3 and width-4 contention figures in the same run, which is the
entire mechanism `defer-to-baseline` depends on to be decidable next cycle without a code change.
Confirmed by inspection: `grep -n "workerCountForCores\|resolveWorkerCount" bench/sweep-contention.bench.test.ts`
returns only comment references, never a call site.

**Commit:** `f248cb1` -- `test(07.1-04): measure main-thread contention under a real in-flight
sweep at workerCount=3 and 4`

**Arm's own cost:** ~2.0-2.7s warm, isolated (`npx vitest run --project bench
bench/sweep-contention.bench.test.ts`), of the 28.78s full local suite total (cap 30,000ms,
9-core sandbox; the CI baseline was 66,527ms before this file existed and plan 05 owns the
overall reduction, not this plan).

## The four required figures (Task 2's own acceptance criteria)

All figures below are **sandbox-informational, NOT the D-17 baseline** (PERF-11):
`hardwareConcurrency=9` on this dev sandbox, not the declared 4-core baseline. Four independent
runs were taken across the session; the most recent full-suite run's figures are the primary
reference below, with the others shown for reproducibility (and one visible, explained outlier).

| Figure | width=3 | width=4 | delta |
|---|---|---|---|
| `sweepDurationUnderLoadMs` (raw) | 476.60 | 354.20 | -122.40ms (-25.7%) |
| `maxRecomputeMs` (raw) vs PERF-07b's 16ms budget | 1.00 | 0.50 | -0.50ms |
| `maxFrameGapMs` (raw) vs PERF-07a's 50ms budget | 16.70 | 16.80 | +0.10ms |
| `coldFirstSweepMs` (raw, the added worker's one-time cost) | 43.50 | 52.40 | +8.90ms |
| `frameCount` (workload frames completed) | 29 | 22 | -7 |

Three additional runs (bench-file-only, for reproducibility), all directionally identical --
throughput improves at width=4, both interactivity figures stay far under budget at both widths,
the added worker's one-time cost is small and comparable at both widths:

- Run A: width=3 `sweepDurationUnderLoadMs=473.60`, `maxRecomputeMs=0.90`, `maxFrameGapMs=16.80`,
  `coldFirstSweepMs=41.80`, `frameCount=29`; width=4 `sweepDurationUnderLoadMs=379.80`,
  `maxRecomputeMs=0.70`, `maxFrameGapMs=16.80`, `coldFirstSweepMs=47.20`, `frameCount=24`.
- Run B: width=3 `sweepDurationUnderLoadMs=489.10`, `maxRecomputeMs=1.10`, `maxFrameGapMs=16.80`,
  `coldFirstSweepMs=58.10`, `frameCount=31`; width=4 `sweepDurationUnderLoadMs=355.30`,
  `maxRecomputeMs=0.30`, `maxFrameGapMs=16.70`, `coldFirstSweepMs=48.90`, `frameCount=23`.
- Run C: width=3 `sweepDurationUnderLoadMs=489.20`, `maxRecomputeMs=1.00`, `maxFrameGapMs=16.80`,
  `coldFirstSweepMs=49.20`, `frameCount=30`; width=4 `sweepDurationUnderLoadMs=354.70`,
  `maxRecomputeMs=0.30`, `maxFrameGapMs=16.80`, `coldFirstSweepMs=46.40`, `frameCount=22`.

**One visible outlier, disclosed rather than discarded (kept disclosed per the coordinator's
explicit direction):** the very first run in this session measured `coldFirstSweepMs=10188.90`
at width=4 (vs `62.80` at width=3 in that same run), a roughly 170x spike not seen in any of the
four subsequent runs (43.50-52.40ms). This reads as a one-time environment warm-up artifact from
that run being the first browser-mode Vitest invocation of the session in this sandbox
(module/dev-server cold-cache effects), not a property of a fourth worker -- immediately
re-running the identical file produced a normal figure, and three further runs since have stayed
in the 43-58ms band at both widths. Recorded here so a reader sees the anomaly and its
explanation rather than a silently cherry-picked clean run.

**What these figures say, read together, per this task's own instruction not to decide on
throughput alone:**

- Throughput: width=4 measures ~19-26% faster sweep duration under load across four runs in this
  sandbox, in the same range as the profile's own theoretical 25% (851.39ms -> 638.54ms at the
  D-17 baseline).
- Interactivity: at both widths, in this sandbox, `maxRecomputeMs` stays under 1.1ms (far under
  PERF-07b's 16ms budget) and `maxFrameGapMs` sits at ~16.7-16.8ms (essentially exactly one frame
  interval, and far under PERF-07a's 50ms ceiling) -- no visible interactivity regression at
  width=4 versus width=3 in this sandbox, across every run.
- The added worker's one-time cost (`coldFirstSweepMs`) is small (tens of milliseconds) and
  comparable at both widths in every clean run, with one large but explained and non-reproducing
  outlier.

**Why this sandbox cannot decide the question.** `hardwareConcurrency=9` here: at 9 cores,
neither `workerCount=3` nor `workerCount=4` is the width production would resolve on this host
(`resolveWorkerCount()` would pick 8), and 9 cores gives the main thread 5-6 spare cores under
either tested width -- nothing like the 4-core baseline's 0-1 spare cores, where a fourth worker
genuinely competes for the last core the main thread needs. A sandbox where interactivity headroom
is this large by construction cannot show what a fourth worker does when the host has almost no
spare capacity to begin with. This is exactly why 07.1-RESEARCH.md's Open Question 2 and this
plan's own `<context>` require the CI run at `hardwareConcurrency=4` before deciding.

## Task 2: the decision -- `defer-to-baseline`

**Decision:** `workerCountForCores` does NOT change on this branch. Whether it changes from
`cores - 1` to `cores` is deferred to plan 07.1-06's CI run at `hardwareConcurrency=4`, decided
against the explicit threshold below.

**Rationale (checkpoint returned by the user):** the sandbox figures are directionally favorable
but structurally uninformative about a 4-core host, since 5 to 6 cores sit spare under either
width here versus near-zero spare on the baseline. A 4-core decision gets made on 4-core
evidence. The one extra CI cycle is worth it.

### The rule plan 07.1-06 executes -- stated so it can act without re-deriving it

Read `bench/sweep-contention.bench.test.ts`'s `sweep-contention-width-3`,
`sweep-contention-width-4` and `sweep-contention-comparison` info lines from the
`hardwareConcurrency=4` CI run (they are already produced by every `npm run bench` invocation,
including CI, because width is parameterized explicitly -- see Task 1 above, no code change is
needed to obtain them). Then:

**Adopt `cores` (change `workerCountForCores` in both `src/sweep/sweep-pool.ts` and
`bench/sweep-pool.ts` together, in one commit, with a PROJECT.md Key Decision citing all four
figures below, not the throughput figure alone) IF AND ONLY IF, at `workerCount=4` on that run:**

1. `maxRecomputeMs` is clearly under PERF-07b's 16ms budget -- with margin comparable to or
   larger than WINDOWS.md's own +/-13% (2sd) single-run noise band, so a borderline pass is not
   read as a clear one.
2. `maxFrameGapMs` is clearly under PERF-07a's 50ms ceiling, same margin standard.
3. Neither figure is measurably worse than the same run's own `workerCount=3` figures -- a
   fourth worker that trades sweep throughput for a visible interactivity cost even on the
   declared baseline is exactly the failure 07.1-RESEARCH.md's Pitfall 3 warns against.
4. `sweepDurationUnderLoadMs` at `workerCount=4` is measurably faster than at `workerCount=3` on
   that same run, so the throughput side of the trade is real on the baseline, not only in this
   sandbox.

**Otherwise, keep `cores - 1` (`keep-the-rule`, the explicit fallback) and record why in a
PROJECT.md Key Decision citing the specific figure(s) that failed the threshold above.** In
particular: if the 4-core run shows `maxRecomputeMs` or `maxFrameGapMs` approaching or exceeding
their budgets at width 4, or shows no measurable throughput gain, that is a direct trigger for
`keep-the-rule`, not a case requiring further judgment calls. Under `keep-the-rule`, plan 07.1-06
must record an escalation (not a pass) if the headline PERF-03 figure then misses the 870ms
target, per this plan's own Task 2 acceptance criteria -- an unproven margin is not spent on an
unmet target.

This is a rule plan 07.1-06 can execute directly against its own CI run's info lines: no further
judgment, re-reading of this sandbox's figures, or re-derivation of the threshold is required.
