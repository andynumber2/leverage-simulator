## Task 1: `bench/sweep-contention.bench.test.ts`

Created an informational-only bench arm (`commands.recordInfoLine` only, never
`commands.recordMeasurement`) that, for each of `BASELINE_WORKER_COUNT` (3) and
`BASELINE_WORKER_COUNT + 1` (4), in a fresh pool:

1. Measures a small (1x1), grid-size-independent cold sweep to isolate the added worker's
   one-time module-evaluation + bundle-fetch cost (`coldFirstSweepMs`).
2. Measures a full 200x50 warm sweep, unloaded (`warmSweepMs`).
3. Starts a second full 200x50 sweep and holds its promise while a `requestAnimationFrame`-driven
   loop repeatedly times one real `runBacktest` call over a real `resolveColumnSeries` result (the
   same kernel call `src/app/state.ts`'s `scheduleRun` performs per coalesced recompute) and the
   wall-clock gap since the previous frame callback -- stopping when the sweep's own promise
   resolves.

Emits one info line per width (`sweep-contention-width-3`, `sweep-contention-width-4`) plus one
comparison line (`sweep-contention-comparison`) naming the deltas. Fails loudly if fewer than 11
frames complete during the in-flight sweep, so no reported max/median rests on a single-sample
artifact (did not trigger: both widths completed 20+ frames in every observed run).

## The four required figures (Task 2's own acceptance criteria)

All figures below are **sandbox-informational, NOT the D-17 baseline** (PERF-11):
`hardwareConcurrency=9` on this dev sandbox, not the declared 4-core baseline. Three independent
runs were taken; the most recent full-suite run's figures are the primary reference below, with
the other two runs shown alongside to demonstrate directional consistency (and one visible
outlier, discussed after the table).

| Figure | width=3 | width=4 | delta |
|---|---|---|---|
| `sweepDurationUnderLoadMs` (raw) | 473.60 | 379.80 | -93.80ms (-19.8%) |
| `maxRecomputeMs` (raw) vs PERF-07b's 16ms budget | 0.90 | 0.70 | -0.20ms |
| `maxFrameGapMs` (raw) vs PERF-07a's 50ms budget | 16.80 | 16.80 | 0.00ms |
| `coldFirstSweepMs` (raw, the added worker's one-time cost) | 41.80 | 47.20 | +5.40ms |
| `frameCount` (workload frames completed) | 29 | 24 | -5 |

Second run (bench-file-only, for reproducibility): width=3 `sweepDurationUnderLoadMs=489.10`,
`maxRecomputeMs=1.10`, `maxFrameGapMs=16.80`, `coldFirstSweepMs=58.10`, `frameCount=31`; width=4
`sweepDurationUnderLoadMs=355.30`, `maxRecomputeMs=0.30`, `maxFrameGapMs=16.70`,
`coldFirstSweepMs=48.90`, `frameCount=23`. Directionally identical to the primary run: throughput
improves at width=4, both interactivity figures stay far under budget at both widths, and the
added worker's one-time cost is small and comparable at both widths.

**One visible outlier, disclosed rather than discarded:** the very first run in this session
measured `coldFirstSweepMs=10188.90` at width=4 (vs 62.80 at width=3 in that same run), a ~170x
spike not seen in either subsequent run (47.20ms and 48.90ms). This reads as a one-time
environment warm-up artifact from that run being the first browser-mode Vitest invocation of the
session in this sandbox (module/dev-server cold-cache effects), not a property of a fourth
worker -- immediately re-running the identical file produced a normal figure. Recorded here so a
reader sees the anomaly and its explanation rather than a silently cherry-picked clean run.

**What these figures say, read together, per this task's own instruction not to decide on
throughput alone:**

- Throughput: width=4 measures ~15-20% faster sweep duration under load in this sandbox, smaller
  than the profile's own theoretical 25% (851.39ms -> 638.54ms at the D-17 baseline), consistent
  with real scaling being less than perfectly linear (07.1-RESEARCH.md assumption A4's own named
  risk).
- Interactivity: at both widths, in this sandbox, `maxRecomputeMs` stays under 1.1ms (far under
  PERF-07b's 16ms budget) and `maxFrameGapMs` sits at ~16.7-16.8ms (essentially exactly one frame
  interval, and far under PERF-07a's 50ms ceiling) -- no visible interactivity regression at
  width=4 versus width=3 in this sandbox.
- The added worker's one-time cost (`coldFirstSweepMs`) is small (tens of milliseconds) and
  comparable at both widths in the two clean runs, with one large but explained and
  non-reproducing outlier.

**Why this sandbox cannot decide the question.** `hardwareConcurrency=9` here: at 9 cores,
neither `workerCount=3` nor `workerCount=4` is the width production would resolve on this host
(`resolveWorkerCount()` would pick 8), and 9 cores gives the main thread 5-6 spare cores under
either tested width -- nothing like the 4-core baseline's 0-1 spare cores, where a fourth worker
genuinely competes for the last core the main thread needs. A sandbox where interactivity headroom
is this large by construction cannot show what a fourth worker does when the host has almost no
spare capacity to begin with. This is exactly why 07.1-RESEARCH.md's Open Question 2 and this
plan's own `<context>` require the CI run at `hardwareConcurrency=4` before deciding.

## What the CI baseline run (plan 07.1-06) would need to show

For `adopt-cores` to be defensible, the `hardwareConcurrency=4` CI run's `sweep-contention`
info lines would need to show, at `workerCount=4`:

- `maxRecomputeMs` clearly under PERF-07b's 16ms budget (not merely under -- with margin
  comparable to WINDOWS.md's own +/-13% (2sd) single-run noise band, so a borderline pass is not
  read as a clear one).
- `maxFrameGapMs` clearly under PERF-07a's 50ms ceiling, same margin standard.
- Both figures not measurably worse than the same run's `workerCount=3` figures -- a fourth
  worker that trades sweep throughput for a visible interactivity cost even on the declared
  baseline is the exact failure Pitfall 3 warns against.
- `sweepDurationUnderLoadMs` at `workerCount=4` measurably faster than at `workerCount=3`, so the
  throughput side of the trade is real on the baseline, not just in this sandbox.

If the 4-core run instead shows `maxRecomputeMs` or `maxFrameGapMs` approaching or exceeding
their budgets at `workerCount=4`, or no measurable throughput gain, `keep-the-rule` is the
correct read regardless of what this sandbox showed -- an unproven margin on the baseline is not
spent on a sandbox-only signal.

## Task 2: the decision (NOT YET MADE)

**Decision:** Whether `workerCountForCores` changes from `cores - 1` to `cores`, in both its
production (`src/sweep/sweep-pool.ts`) and bench (`bench/sweep-pool.ts`) declarations.

**Options** (full detail in `07.1-04-PLAN.md` Task 2):

| Option | Summary |
|---|---|
| `adopt-cores` | Change the rule to `cores`, in both declarations, citing the interactivity evidence above alongside the throughput figure in a PROJECT.md Key Decision. |
| `keep-the-rule` | Keep `cores - 1`; record why; plan 07.1-06 must record an escalation (not a pass) if the headline PERF-03 figure then misses 870ms. |
| `defer-to-baseline` | Defer the choice to plan 07.1-06's CI run at `hardwareConcurrency=4`, per an explicit stated threshold rather than re-litigating. |

**This executor's read of the evidence, offered as input to the decision, not as a selection made
on the plan's behalf:** the sandbox figures are directionally favorable to `adopt-cores`
(throughput improves, no visible interactivity cost) but are measured on a host structurally
unable to exercise the contention this decision is actually about (9 cores vs the 4-core
baseline's near-zero spare capacity). Per this plan's own instruction ("If the sandbox figures
are ambiguous, say so and choose `keep-the-rule`"), a favorable-but-structurally-uninformative
sandbox result reads closer to `defer-to-baseline` than to an outright `adopt-cores` -- the
sandbox cannot rule out an interactivity cost that would only appear when spare capacity is
scarce. `defer-to-baseline`'s own threshold (stated above, in "What the CI baseline run would
need to show") gives plan 07.1-06 a rule to execute rather than a re-litigation.
