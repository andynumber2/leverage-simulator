# Phase 07.1 Plan 02: Combined-violation reporting and structural partition-coverage proof Summary

**`assertRunInvariants` now reports a budget-verdict failure and a runtime-cap breach in one message instead of masking whichever check runs second, and `partitionColumns`' exactly-once column coverage is proven structurally in the fast Node unit project rather than sampled through the pool.**

## Performance

- **Duration:** ~20 min (includes a real `npm run build` + `npm run bench` verification pass)
- **Tasks:** 2
- **Files modified:** 4 (1 created, 3 modified)

## Accomplishments

- `assertRunInvariants` (`bench/report.ts`) collects the verdict-fail violation and the runtime-cap violation into one list and throws once with both, instead of the first `throw` masking the second. The PERF-08 coverage gate, the score-coherence block, and the PERF-03 host-width guard keep their exact relative order and each still throws immediately at its own point in the function — but now folds any already-collected violation text into its own thrown message, so a run that is both over budget and hits one of those later gates still names the earlier failure too.
- `partitionColumns` (`src/sweep/sweep-pool.ts`) is now exported, unchanged except for the `export` keyword and an added doc-comment sentence. `tests/sweep/partition.test.ts` proves, at every worker count 1 through 8 at the real 200-column width (plus the degenerate 0/1/below-chunk-count cases), that every column index belongs to exactly one chunk: no gap, no duplicate, contiguous ascending ranges, and each chunk's `entryDates` positionally matches its `columnIndices`. This closes the hole `bench/sweep.bench.test.ts`'s 50-cell coprime-stride equality check leaves open — that stride samples 50 of 10,000 cells and can miss an affected column entirely, and a skipped or double-counted column still leaves every written cell finite, so neither of the bench's existing structural guards catches it.
- Confirmed the fix live: this dev sandbox's `npm run bench` run (after `npm run build`, so PERF-08 measured against a real preview build) threw `assertRunInvariants: 1 row(s) failed budget: PERF-04; total bench runtime 110861ms exceeds the declared cap of 30000ms (D-08): repeat cost has crept; raising the cap requires a recorded decision, not a silent edit` — one error, both violations named. **Yes, the newly-unmasked runtime-cap breach now reports on this host, at 110,861ms against the 30,000ms cap** (this sandbox's own figure; not the D-17 baseline, per PERF-11 — this host is not `hardwareConcurrency=4`, and PERF-04/PERF-09 also failed here on what look like resource-constrained-sandbox timeouts, not a regression this plan introduced).
