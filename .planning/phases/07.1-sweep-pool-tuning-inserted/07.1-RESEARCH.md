# Phase 7.1: Sweep Pool Tuning (INSERTED) - Research

**Researched:** 2026-08-23
**Domain:** Worker-pool throughput tuning for a fixed compute workload; bisection-solver cost reduction; bench-harness invariant ordering
**Confidence:** HIGH for what the code and CI artifacts already prove; MEDIUM/LOW for anything that requires a profiling run this research did not execute (flagged inline)

## Summary

This phase has one job: make `bench/sweep.bench.test.ts`'s PERF-03 row read `verdict=pass` on
the real D-17 baseline (`hardwareConcurrency=4`, `workerCount=3`), for both the zero-contribution
headline sweep (currently 1168.59ms / 116.9% of the 1000ms budget) and the contribution-schedule
`solveIrr` branch (currently 8961.84ms / ~8.96x over budget), without moving `thresholdMs`,
`NOMINAL_REFERENCE_MS`, or any other calibration/budget constant.

Reading the shipped code changes the picture PROJECT.md's "PERF-03 D-17 baseline escalation"
row leaves open. That row states the shared-root-cause theory is "an inference from the pool
configuration, not a profiled finding." Two things follow from actually reading
`src/sweep/sweep-pool.ts`, `sweep.worker.ts`, and `resolve-column-series.ts` closely:

1. **Transfer and per-column resolution are already close to optimal.** Every chunk result
   crosses the worker boundary as a `Comlink.transfer`red `ArrayBuffer`, never structured-cloned
   (`[VERIFIED: src/sweep/sweep-pool.ts:367]`, `[VERIFIED: src/sweep/sweep.worker.ts:282]`). The
   bundled series data never crosses `postMessage` at all -- each worker `fetch()`es and decodes
   it once, cached for the worker's lifetime (`[VERIFIED: src/sweep/sweep.worker.ts:106-111]`).
   `resolveColumnSeries` runs exactly once per column, not once per cell -- confirmed by reading
   `computeChunkMetrics`'s loop structure (`[VERIFIED: src/sweep/sweep.worker.ts:184-198]`), and
   no column is ever resolved twice across chunks because `partitionColumns` assigns each column
   to exactly one contiguous chunk (`[VERIFIED: src/sweep/sweep-pool.ts:117-139]`). There is no
   "resolve-column-series work repeated per chunk" problem to fix.
2. **The bench's own entry-date axis is a poor test of load-imbalance-driven tuning.**
   `bench/sweep.bench.test.ts` deliberately restricts its 200-column axis to the *first* 200
   trading sessions of the extended tier and asserts every column's bar count is within 99.15% of
   the longest column's (`[VERIFIED: bench/sweep.bench.test.ts:100-185]`, quoted below). That
   means every one of the 12 chunks costs almost exactly the same, so a naive equal-column-count
   partition is already close to balanced *for this specific benchmark*. This is real, deliberate
   test design (01-02-SUMMARY.md's "no cell flattered by a short window" rule), but it means the
   research prompt's premise -- "later entry dates run shorter series... a naive equal-cell-count
   partition load-imbalances" -- describes the **production live sweep** (`src/app/state.ts`'s
   `resolveSweepEntryDates`, which spreads 200 columns evenly across the *entire* history, so late
   entries genuinely are much shorter, `[VERIFIED: src/app/state.ts:359-374]`), not the PERF-03
   benchmark itself. Any partition-shape change must be judged against both axes separately, and
   the plan should not expect load-balancing alone to move the PERF-03 number by much.

Given those two findings, the honest read of where the 952.40ms raw headline figure goes is:
almost entirely kernel compute (the per-bar `runBacktest` recurrence, run ~250M bar-updates total
across 10,000 cells x ~24,900 bars, divided across 3 workers), not pool/dispatch/transfer
overhead. Chunk payloads are tiny (a ~800-cell chunk's result buffer is ~10KB, transferred not
cloned; the request object is a handful of numbers and 16-17 date strings, cloned but negligible).
**This means "pool tuning" as PROJECT.md names it will mostly cash out as *worker-count* tuning
(using more of the 4 available cores), not chunk-shape or transfer-discipline tuning** -- and that
in turn is not free: `workerCountForCores`'s `cores - 1` rule exists specifically so the main
thread stays free to paint/respond during an in-flight sweep (PERF-04/06/07's contract). No
existing bench exercises a real interactive drag concurrently with an in-flight sweep at
`workerCount=4`, so this lever needs new evidence before it can be adopted, not just a constant
change.

The `solveIrr` branch is the harder problem and pool tuning alone cannot close it. Reading
`src/metrics/irr.ts` closely: `npv()` is re-evaluated on the order of ~34 bisection iterations
(TOLERANCE=1e-9 over an 11-unit bracket needs roughly `log2(11/1e-9) ~= 33.4` halvings) times up
to ~1,176 cash flows (one per elapsed month, for a ~98-year hold) times 10,000 cells -- on the
order of 400M `Math.exp()` calls, which plausibly accounts for most of the observed 7.3s raw
figure on its own (`[ASSUMED: reasoned from code, not profiled this session]`). A 3-worker,
kernel-compute-bound branch like this has, at best, ~3x of parallel headroom already spent; no
combination of chunk/transfer tuning gets an 8.96x-over-budget branch under budget. The bracket
tolerance and iteration cap are explicitly Claude's-Discretion values (04-CONTEXT.md,
`[VERIFIED: src/metrics/irr.ts:9-13]`), so tightening them is available without a new Key
Decision; a faster-converging solver (Newton/Brent) is not -- D-08 explicitly rejected a
two-solver path on the stated premise that IRR "runs once per parameter change... where speed is
not the constraint," and the sweep callsite invalidates that premise, so revisiting it needs its
own recorded decision, not a silent edit.

**Primary recommendation:** Treat this phase as two separable problems with different ceilings.
For the headline row: get a real profiled breakdown first (cheap, no new dependency -- the harness
already has `recordInfoLine`), then decide whether `workerCount=4` is safe to adopt as a deliberate,
disclosed change to `workerCountForCores` (gated on a new concurrent-drag-during-sweep
measurement), because chunk/transfer tuning alone has limited headroom against a near-uniform,
kernel-bound axis. For the `solveIrr` branch: tighten the bisection tolerance/iteration cap first
(cheap, in-scope, no new Key Decision), measure, and if that alone does not close ~9x, escalate
with a named remaining lever (Newton-with-bisection-fallback, scoped to the sweep callsite only)
rather than pretend pool tuning reaches it.

### Pattern 2: Diagnostic instrumentation must live outside the timed window

**What:** Any new `performance.now()` instrumentation added to answer Success Criterion 1's
"measured breakdown" must not run inside the same `measureMinOfN` call that produces the gated
PERF-03 `MeasurementRow`. Two options, ranked:
1. A **separate, `recordInfoLine`-only bench test** that calls `createSweepPool()` fresh, times
   construction, times the first (cold-bundle) `runSweep` call, then a second (warm) call, and
   separately calls `computeChunkMetrics` directly (already exported, pure, synchronous,
   `[VERIFIED: src/sweep/sweep.worker.ts:167]`) against one real chunk's inputs to get a
   zero-pool-overhead per-chunk kernel figure. None of this touches the code path
   `bench/sweep.bench.test.ts` measures for the gated row.
2. If per-chunk dispatch/transfer/idle needs to be split further: have `runChunk` self-report its
   own in-worker `computeChunkMetrics` wall time back to the main thread (a second, tiny Comlink
   return value or an appended timing field). This is two extra `performance.now()` calls per
   chunk (12 chunks total) -- nanosecond-scale overhead against a ~950ms figure, and the same kind
   of disclosed-but-present instrumentation this project already accepts elsewhere (e.g.
   `batchSize` disclosure in `07-PERF-03-BASELINE.md`'s `REJECTED_POLYGON_BATCH_SIZE` change). If
   the plan chooses to leave this instrumentation permanently in `runChunk` (simplest, one code
   path), it must be disclosed in the same way; if it chooses to gate it behind a debug flag used
   only by the diagnostic test, that avoids any argument about it being present in the gated path
   at all. Either is legitimate; the plan should pick one and say why.
**When to use:** Any time a measurement is added to explain, rather than gate, a workload.
**Anti-pattern this avoids:** Wrapping `performance.now()` calls around sub-steps *inside* the
same closure `measureMinOfN` times for PERF-03 itself. That would inflate the gated figure with
instrumentation overhead and make the "no relaxation" claim in Success Criterion 3 harder to
defend (a slower-because-instrumented measurement is not a real regression, but it looks like one
in the artifact, and a change that looks like it moved the number without moving the code is
exactly the kind of thing PERF-01a exists to catch).

### Anti-Patterns to Avoid
- **Assuming the bench's near-uniform entry-date axis represents the live app's sweep.** They are
  materially different (`bench/sweep.bench.test.ts`'s first-200-days axis vs
  `src/app/state.ts`'s evenly-spread-across-full-history axis). A partition-shape change validated
  only against the bench's axis could still load-imbalance badly on the live app's axis. If the
  plan changes `CHUNKS_PER_WORKER` or partitioning logic, it should reason about (or test against)
  both shapes, not just the one PERF-03 gates.
- **Treating `workerCountForCores`'s `cores - 1` rule as a free constant to bump.** It is a
  deliberate interactive-safety margin (PERF-04/06/07), not an arbitrary choice. No existing bench
  exercises a drag concurrently with an in-flight sweep at any worker count, so there is currently
  no evidence either way about `workerCount=4`'s effect on interactivity. Treat adopting it as
  requiring new evidence, not as a config edit.
- **Reducing `solveIrr`'s `MAX_ITERATIONS`/`TOLERANCE` without checking displayed precision.**
  Legitimate (Claude's Discretion, not load-bearing correctness) but must be checked against what
  the UI actually displays (a percentage, presumably rounded to a small number of decimal places)
  before assuming a looser tolerance changes nothing the user sees.

## Common Pitfalls

### Pitfall 1: A faster wrong answer passing as an improvement
**What goes wrong:** A chunk-shape or worker-count change silently drops or double-counts cells,
or a stale-generation race under the new shape lets a superseded chunk's cells reach the grid.
**Why it happens:** `mergeChunkResult`'s stale check and `partitionColumns`'s column accounting
are both correct today, but any restructuring of chunk boundaries or the drain-queue loop is
exactly the kind of change that could silently break the "every column belongs to exactly one
chunk" invariant this research relied on above.
**How to avoid:** `bench/sweep.bench.test.ts` already has two structural guards that survive a
partition-shape change unmodified: the 10,000-finite-cells-no-holes test (test 2) and the
50-cell coprime-stride pool-vs-serial equality test (test 3, `SERIAL_REFERENCE_STRIDE=197`,
`[VERIFIED: bench/sweep.bench.test.ts:84-85]`). Both call `pool.runSweep` on whatever
`pool` was constructed with, so re-running them after a `workerCount`/`CHUNKS_PER_WORKER` change
is sufficient re-validation -- no new equality test is structurally required, only confirmation
the existing two still pass. **Do not weaken or skip these before trusting a new timing figure.**
**Warning signs:** A timing improvement that arrives together with a change to `finiteCount`,
`ruinedCount`, or a shift in `SERIAL_REFERENCE_STRIDE`'s sampled cells' expected values.

### Pitfall 2: A measurement that moves cost outside its own window
**What goes wrong:** "Worker reuse" or "warm-start" changes that make PERF-03's `measureMinOfN`
loop look faster because they shifted real cost to `beforeAll` (untimed setup) or to production's
lazy pool-construction moment, rather than eliminating it.
**Why it happens:** The bench already deliberately excludes worker construction from the timed
loop (`pool = createSweepPool(...)` in `beforeAll`, `[VERIFIED: bench/sweep.bench.test.ts:263-270]`)
-- this is *correct* today because it matches production's own persistent-pool contract (a real
user's session also constructs the pool once, on first sweep-mode entry, and reuses it for every
sweep after). The risk in this phase is a *different* move: e.g., precomputing something at
`beforeAll` time that a real user's session would have to pay for on every parameter change (not
just the first), which would make the bench faster without describing the real per-sweep cost.
**How to avoid:** For any change that removes work from the timed `measureMinOfN` closure, ask
"does the production `runSweepNow()` path (src/app/state.ts) also get to skip this on every
sweep, or only once per session?" If the answer is "only once per session," it belongs in
pool-construction-adjacent code (already excluded, correctly) -- not inside `runSweep` itself.
**Warning signs:** A large timing win that has no matching change to what
`computeChunkMetrics`/`runBacktest` actually compute per cell.

### Pitfall 3: `workerCount=4` benchmarked in isolation, adopted without interactivity evidence
**What goes wrong:** PERF-03 passes at `workerCount=4`, but a real user dragging the leverage
slider while a background sweep runs experiences dropped frames or a delayed cancel, because the
main thread now shares 4 of 4 cores with the sweep instead of 3.
**Why it happens:** `bench/perf-07.bench.test.ts` (drag interaction) and
`bench/sweep-progressive.bench.test.ts` (PERF-04/06) are separate test files that never run a
drag and a sweep concurrently, `[VERIFIED: bench/perf-07.bench.test.ts, bench/sweep-progressive.bench.test.ts]`
-- there is currently no automated evidence either way about this interaction.
**How to avoid:** Either (a) add a new concurrent-drag-during-sweep measurement before adopting
`workerCount=4` as production's default, or (b) keep `workerCountForCores` unchanged for
production and treat any `workerCount=4` win as PERF-03-bench-specific, which reopens the exact
problem quick-260818-v2d's `BASELINE_WORKER_COUNT` was written to prevent (a bench figure that no
longer represents what production actually deploys). Both are legitimate; silently picking (a)'s
conclusion without doing the work is not.
**Warning signs:** A PROJECT.md Key Decision that changes `workerCountForCores`'s formula citing
only the PERF-03 bench figure, with no PERF-04/06/07 evidence cited alongside it.

### Pitfall 4: Tightening `solveIrr`'s tolerance changes a number the user actually sees
**What goes wrong:** Reducing `TOLERANCE`/`MAX_ITERATIONS` shifts the solved rate by more than the
UI's own display rounding, so a permalink's displayed IRR changes between builds -- a correctness
regression for SHARE-03's determinism guarantee, not just a performance tweak.
**Why it happens:** `TOLERANCE=1e-9` is far tighter than any percentage display needs; loosening
it is safe in principle, but "safe in principle" is not the same as verified against the actual
formatted output.
**How to avoid:** Before changing either constant, find where the annualized metric is formatted
for display (percentage, N decimal places) and assert the change is invisible at that precision
across a representative sample of cells, not just that the raw float moved by less than the new
tolerance.
**Warning signs:** `tests/metrics/irr.test.ts` or a permalink-determinism test failing after the
tolerance change.

### Where `assertRunInvariants` currently masks the runtime-cap breach
```typescript
// Source: bench/report.ts:383-389 [VERIFIED] -- the verdict-fail gate, checked FIRST
const failing = rows.filter((r) => r.verdict === 'fail')
if (failing.length > 0) {
  const failingIds = failing.map((r) => r.budgetId).sort((a, b) => a.localeCompare(b))
  throw new Error(
    `assertRunInvariants: ${failing.length} row(s) failed budget: ${failingIds.join(', ')}`,
  )
}
// ... PERF-08 coverage check, score-coherence check ...
// Source: bench/report.ts:479-485 [VERIFIED] -- the runtime-cap gate, checked LAST
if (totalRuntimeMs > BENCH_TOTAL_RUNTIME_CAP_MS) {
  throw new Error(
    `assertRunInvariants: total bench runtime ${totalRuntimeMs}ms exceeds the declared cap ` +
      `of ${BENCH_TOTAL_RUNTIME_CAP_MS}ms (D-08): repeat cost has crept; raising the cap ` +
      'requires a recorded decision, not a silent edit',
  )
}
```
Because JavaScript `throw` exits the function on the first failing check, a run with BOTH a
verdict-fail AND a runtime-cap breach (exactly what CI run 32654061079 recorded: `verdict=fail`
at 1168.59ms AND `totalRuntimeMs=43,259ms` against the 30,000ms cap) only ever reports the first
one. **The fix is to collect both violations and report them together, not to reorder which one
wins.** Reordering (checking the cap first) would just flip which one gets masked. A minimal,
test-compatible shape:
```typescript
// Illustrative, not prescriptive -- the plan should verify against tests/report.test.ts's
// existing `.toThrow(regex)` assertions (all substring-based, so a combined message that still
// contains each expected substring keeps every existing test green, [VERIFIED: tests/report.test.ts]).
const violations: string[] = []
if (failing.length > 0) {
  violations.push(`${failing.length} row(s) failed budget: ${failingIds.join(', ')}`)
}
if (totalRuntimeMs > BENCH_TOTAL_RUNTIME_CAP_MS) {
  violations.push(
    `total bench runtime ${totalRuntimeMs}ms exceeds the declared cap of ` +
      `${BENCH_TOTAL_RUNTIME_CAP_MS}ms (D-08): repeat cost has crept; raising the cap requires ` +
      'a recorded decision, not a silent edit',
  )
}
if (violations.length > 0) {
  throw new Error(`assertRunInvariants: ${violations.join('; ')}`)
}
```
This must be placed considering the existing PERF-08-coverage and score-coherence checks, which
currently run *between* the verdict-fail check and the runtime-cap check and are themselves
deliberately ordered relative to the PERF-03 host-width guard (see the code's own comments at
`bench/report.ts:336-341` and `:394-397`, `[VERIFIED]`). The safest change is additive (collect
the verdict-fail and runtime-cap violations together, leave the PERF-08/score-coherence/host-width
ordering exactly as-is), not a full reorder of the function.

## Open Questions

1. **How much of the headline 1168.59ms is genuinely kernel-bound vs pool overhead?**
   - What we know: chunk payloads are small and transferred, not cloned; column resolution is
     already amortized across 50 rows; the entry-date axis is near-uniform.
   - What's unclear: the exact split, which only a real profiling run (Success Criterion 1) can
     supply.
   - Recommendation: implement the diagnostic bench arm described under Pattern 2 as this phase's
     first task, before choosing between worker-count and chunk-shape levers.

2. **Does `workerCount=4` regress PERF-04/06/07 under a real concurrent drag-during-sweep
   scenario?**
   - What we know: no existing bench exercises this combination.
   - What's unclear: whether headless-Chromium-under-Playwright's scheduling is even a faithful
     proxy for a real user's OS-level thread scheduling here, given the bench measures a batch
     call with no actual competing UI paint work in the timed window.
   - Recommendation: either build a minimal concurrent-measurement bench arm, or make the
     `workerCount=4` adoption decision explicitly conditional and record the untested risk in the
     PROJECT.md Key Decision rather than silently assuming safety.

3. **Is the `solveIrr` branch's per-cell cost actually uniform across the bench's 200 columns,
   or does it vary meaningfully within the tested axis?**
   - What we know: all 200 columns are near the extended tier's earliest date, hold-to-end-of-data
     -- so cash-flow counts should be close to uniform (~1,176 flows) across the whole tested axis,
     unlike the production app's full-history-spread axis.
   - What's unclear: whether this uniformity holds exactly, or whether some columns' contribution
     schedules resolve differently near calendar-gap edges.
   - Recommendation: the profiling arm from Success Criterion 1 should also cover the
     contribution-schedule sweep, not only the headline sweep, given how much larger its overrun
     is.
