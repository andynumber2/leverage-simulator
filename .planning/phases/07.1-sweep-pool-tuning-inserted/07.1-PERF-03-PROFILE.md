- **This residual is not resolved by this profile.** It is not worker-startup (Section on the
  worker-startup question below shows that cost is already excluded from the measured window). It
  is larger than the profile's own directly-measured pool-overhead figure predicts at constant

  count (`chunkBufferByteLength`, four segments per cell) while the profile's own overhead figure
  was measured at a much smaller buffer size (1200 cells vs 10,000), so per-chunk transfer cost is
  not actually constant the way the dispatch-count model assumes; or per-column kernel cost is not
  perfectly linear as each chunk's column span widens from roughly 2 columns (profile arm, 24 cols
  / 12 chunks) to roughly 16-17 columns (full grid, 200 cols / 12 chunks), which could shift cache
  or GC behavior inside `computeChunkMetrics`'s per-column loop. This document states both as
  candidates it did not isolate, not as a conclusion.

**The worker-startup question, stated plainly** (`hardwareConcurrency=4`): `workerStartupMs`
(224.80ms, derived as `coldSweepMs - warmSweepMs`) and the gated row's own
`measurementExcludesWorkerConstruction=true` flag are **not the same quantity**, and this document
does not conflate them. Worker *construction* -- the `new Worker(...)` call inside
`createSweepPool` -- is genuinely excluded from the timed window by construction: the pool is built
once in `beforeAll`, outside `measureMinOfN` (`[VERIFIED: bench/sweep.bench.test.ts]`), and this
profile's own `poolConstructionMs` (0.20ms) shows that call itself is nearly free. What
`workerStartupMs` actually measures is different: each worker's module evaluation plus its
one-time `loadBundleFromFetch()` call (`getBundle()`, cached for the worker's lifetime,
`[VERIFIED: src/sweep/sweep.worker.ts:101-111]`) -- the real cost of a worker's *first* chunk.

Whether that cost sits inside or outside the gated PERF-03 window is answered by reading
`bench/sweep.bench.test.ts`'s own test order, not by the `measurementExcludesWorkerConstruction`
flag: the shared `pool` (constructed once in `beforeAll`) is exercised by two correctness tests
(`sweep pool: full grid has 10,000 finite cells...`, `sweep pool: pool-computed cells match a
serial reference sample...`) BEFORE the PERF-03 test's own `measureMinOfN(REPEAT_COUNT, ...)` loop
begins (`[VERIFIED: bench/sweep.bench.test.ts:284, :316, :331]`). Those two tests call
`pool.runSweep` first, so every worker's bundle fetch and module evaluation is already warm by the
time PERF-03's own 5 repeats start. **This cost is inside neither the gated measurement window nor
outside it by accident: it is paid off, once, by the two correctness tests that already run first
in the same file, on the same shared pool.**

**The consequence for later plans, stated per this plan's own instruction:** per
07.1-RESEARCH.md's Pitfall 2, moving cost outside a timed window is only legitimate when
production's own `runSweepNow()` path (`src/app/state.ts`) also gets to skip that cost on every
sweep, not just the first one of a session. It does: a real user's session constructs the pool
once, on first sweep-mode entry, and every worker's bundle fetch happens once per session, on that
first sweep -- exactly the same amortization the bench already exhibits by accident of test
ordering. **The test that decides this, restated for whoever tunes next:** does a change move
`getBundle()`'s cost to run on every `pool.runSweep()` call rather than once per worker lifetime?
If yes, that is a relaxation dressed as an optimization and must be refused. If a change only
reorders *when within a session* the existing once-per-worker cost lands (e.g., a real warm-up
sweep before the first user-visible one), that is legitimate amortization, matching what already
happens today. No code in this plan touches this path; it is recorded here as evidence, not acted
on.

## 5. What the profile says, and what it aims at

**Zero-contribution (CAGR) branch, `hardwareConcurrency=4`:** the measured split is 72.2% kernel
compute (`idealParallelMs=851.39ms` of the measured `1179.70ms`) and 27.8% overhead-and-residual
(`328.31ms`), of which only 54.33ms is directly attributable to the profile's own measured pool
overhead at constant chunk count -- the remaining 273.98ms is an unresolved residual (Section 2).

**CORRECTED, 07.1-06: the 25.00% projection below was measured and refuted.** The paragraph
originally here projected a fourth worker's theoretical gain over the ideal-parallel floor at
exactly 25.00% (`851.39ms -> 638.54ms`, the linear-scaling arithmetic `1 - workerCount/(workerCount+1)
= 1 - 3/4`), and that same paragraph's own text already flagged this as confirming
07.1-RESEARCH.md assumption A4's "roughly 25%" figure was that arithmetic, not a separately
profiled number -- the flag was correct to raise; the arithmetic did not hold. The authoritative
D-17 baseline run this projection was written to be tested against (CI run 32676218114,
`hardwareConcurrency=4`, `workerCount=4`) measured the PERF-03 headline row at 1191.34ms
normalized -- inside the width-3 spread (1115.92 to 1208.38ms across three runs), not below it,
and nowhere near the projected 638.54ms. `workerCountForCores` was reverted to `cores - 1` as a
result. See `07.1-PERF-03-BASELINE.md` section 8 for the full measurement and the two independent
grounds for the revert. The reasoned account of why the linear-scaling arithmetic failed: it
assumes a fourth worker finds spare idle capacity, and a 4-core CI runner running a headless
browser harness (the browser main thread and the Playwright-driven test process both compete for
the same four cores the sweep's workers also want) does not have that spare capacity to give.
This is offered as the most plausible account, not as a profiled mechanism -- nothing in this
phase profiled the contention directly. This profile's other findings in this section (the
72.2%/27.8% kernel-compute-versus-overhead split, the 273.98ms unresolved residual, and 07.1-RESEARCH.md
Pitfall 3's untested concurrent-drag risk) all stand; only the worker-count conclusion drawn from
them is superseded.

**Original text, preserved for the record, now refuted by measurement:** "The lever this points at
is worker count, not chunk-shape/overhead tuning. A fourth worker's theoretical gain over the
ideal-parallel floor is exactly 25.00% (`851.39ms -> 638.54ms`, the linear-scaling arithmetic
`1 - workerCount/(workerCount+1) = 1 - 3/4`), confirming 07.1-RESEARCH.md assumption A4's 'roughly
25%' figure is that same arithmetic, not a separately profiled number. 638.54ms clears the 870ms
target with real margin (231.46ms). By contrast, even eliminating the entire measured-plus-residual
overhead (328.31ms) at `workerCount=3` only reaches 851.39ms -- under 870ms, but by a margin
(18.61ms) far smaller than WINDOWS.md's own +/-153ms (2 sigma) noise band on this figure, so
overhead reduction alone cannot be trusted to close this gap durably. This profile does not itself
prove `workerCount=4` is safe: `CHUNKS_PER_WORKER` is a per-worker constant, so a fourth worker
also raises total chunk count from 12 to 16, changing the per-chunk overhead this profile measured
at 12 chunks in a direction this profile did not test; and 07.1-RESEARCH.md's own Pitfall 3 (no
concurrent-drag-during-sweep evidence at any worker count) remains completely untested here. The
margin this branch's split can reach: worker count is the lever with real headroom against 870ms;
a new `workerCount=4` measurement, not this extrapolation, is what would confirm it."

**`solveIrr` branch, `hardwareConcurrency=4`:** the measured split is roughly 70.5% kernel compute
by the same ideal-parallel accounting (`6182.50ms` of the measured `8769.00ms`) and 29.5%
overhead-and-residual (`2586.50ms`). **Worker count alone cannot close this branch:** even the
4-worker ideal-parallel floor (`4636.88ms`) is roughly 5.33x the 870ms target. The lever this
branch's split points at is the `solveIrr` convergence criterion itself.

`npvEvaluationsPerSolve` measured **105.01**, roughly 3.14x 07.1-RESEARCH.md's naive `log2(11 /
1e-9) ~= 33.4` estimate. Reading `src/metrics/irr.ts` explains the gap: the convergence test is
`Math.abs(npvMid) < TOLERANCE` where `TOLERANCE=1e-9` is a **dollar-denominated NPV magnitude**,
not a bracket-width test on the rate itself (`hi - lo < tolerance`). For cash flows in the
thousands to tens of thousands of dollars over holds up to roughly 98 years, driving `|npv|` below
`$1e-9` requires far more refinement than shrinking an 11-unit rate bracket to `1e-9` would, so the
loop almost always exhausts `MAX_ITERATIONS=100` (100 loop iterations plus the 2 initial bracket
evaluations plus the solver's own branch overhead land at the measured 105.01) rather than
converging early near RESEARCH's roughly 33-34-iteration estimate. **A bracket-width convergence
test (`hi - lo < 1e-9` in rate units) would plausibly land near that roughly 33-34-iteration count
instead** -- this is the corrected lever, not the tolerance value itself.

The reachable margin: applying the measured 3.14x reduction factor to the branch's extrapolated
full-grid serial cost (`18547.5 / 3.14 = 5907.5ms`) and then the 4-worker ideal-parallel floor
(`5907.5 / 4 = 1476.9ms`) still lands roughly 1.7x over the 870ms target. **A bracket-width
convergence fix, even combined with a fourth worker, is not sufficient by this profile's own
arithmetic.** A further reduction remains necessary: either a looser dollar-tolerance verified
against actual display precision (07.1-RESEARCH.md Pitfall 4), or the Newton-with-bisection-fallback
solver 07.1-RESEARCH.md's Alternatives table names, scoped to the sweep callsite only per that
research's own scoping note.

**Disposition of 07.1-RESEARCH.md's assumptions, by name, `hardwareConcurrency=4`:**

  **confirmed.** The measured `npvEvaluationsPerSolve` (105.01) is a real, batch-cleared

says nothing about the production live sweep's full-history-spread axis (Section 6).

## 6. Levers this profile rules out

- **Transfer discipline.** Already zero-copy in both directions via `Comlink.transfer`
  (`[VERIFIED: src/sweep/sweep-pool.ts, src/sweep/sweep.worker.ts]`, 07.1-RESEARCH.md Pattern 1).
  No figure in this profile suggests transfer cost is a meaningful fraction of either branch's
  overhead; the residual gap in Section 2 is not attributed to transfer, and this profile found no
  measurement pointing at it as the cause.
- **Per-column resolution.** Already resolved exactly once per column inside
  `computeChunkMetrics`'s loop structure (`[VERIFIED: src/sweep/sweep.worker.ts:184-198]`), not
  once per cell. Nothing in this profile's per-cell figures (`perCellKernelUs`, `cashFlowCount`
  uniformity) suggests repeated resolution work.
- **Chunk-shape rebalancing on the bench's own near-uniform axis.** The extended tier's
  first-200-session axis keeps every column within 99.15%+ of the longest column's bar count
  (07.1-RESEARCH.md, `[VERIFIED: bench/sweep.bench.test.ts]`), and this profile's own
  `cashFlowCountRatio=1.00` extends the same near-uniformity finding to the `solveIrr` branch
  specifically. 12 near-identical chunks have essentially no load-imbalance headroom to rebalance
  away on this axis. **This ruling does not transfer to the production live sweep's axis**
  (`resolveSweepEntryDates` in `src/app/state.ts`, 200 positions spread across the whole bundled
  history), which is genuinely non-uniform and a structurally different axis from the one PERF-03
  gates -- a partition-shape judgement made against the bench's uniform axis says nothing about the
  live app's non-uniform one.
- **Worker-startup / bundle-fetch reduction.** Measured at 224.80ms (`workerStartupMs`, Section 2),
  but already excluded from the gated PERF-03 measurement window by the existing test order in
  `bench/sweep.bench.test.ts` (the two correctness tests warm the shared pool before PERF-03's own
  `measureMinOfN` loop begins). There is no headroom left to spend here against the PERF-03 figure
  specifically: this cost would only move the wall-clock time of a real user's very first sweep of
  a session, a different (and currently unmeasured against any budget) concern.

Every figure in this document states its own `hardwareConcurrency` (4, the D-17 baseline, unless
marked otherwise). No dev-sandbox figure is presented as a baseline figure (PERF-11). This document
closes ROADMAP success criterion 1: the 4-core baseline sweep's wall clock is now a measured
breakdown, for both branches, not an inference.
