**Verdict, stated plainly: FAIL, on all four runs, at both worker widths.** The width-3 mean
normalized figure is `(1120.86 + 1208.38 + 1115.92) / 3 = 1148.39ms`; the width-4 run measured

measurable PERF-03 headline improvement**. This is the first and more important ground for the
revert recorded in section 6.

**The normalization stability point, stated because WINDOWS.md entry 2's own band depends on it
and PERF-01a's no-retuning prohibition rests on it being true:** the four runs' raw `measuredMs`
figures swing from 879.10ms to 1180.00ms (roughly 879 to 1180, a 34% spread, largely tracking
each run's own `calibrationScore`, itself ranging 0.7275 to 1.0550), while the four `normalizedMs`
figures cluster tightly at 1115.92 to 1208.38ms (roughly 4% spread). Run 32673398579's own raw
figure, 879.10ms, is **under the 1000ms budget** -- a reader looking only at the raw number would
call that run a pass -- yet its normalized figure (1208.38ms) is the worst of the four, correctly
failing, because that run drew the fastest host (`calibrationScore=0.7275`, the lowest of the
four, meaning the calibration loop itself ran slowest, meaning this CI runner's other work was
comparatively fast that run). `normalize()` is doing exactly the job it exists to do: collapsing
host-speed variance so the same code reads consistently regardless of which runner it drew, and
the four-run record above is the clearest demonstration available in this phase that retuning
`NOMINAL_REFERENCE_MS` or any other calibration constant in response to a single measurement (the
thing PERF-01a forbids) would be reading the wrong signal -- the raw number moves with the runner,
the normalized number does not, and 1148ms-vs-1191ms is a real, small, code-driven difference
inside that noise floor, not something a calibration retune could or should chase.

## 8. The revert

Both independent grounds below fired; the first is the more important finding and is why this
decision does not lean on the second alone.

**Ground 1 (primary): width 4 produced no measurable PERF-03 improvement.** Section 2's four-run
table shows the width-4 run (1191.34ms) landing inside the width-3 spread (1115.92 to 1208.38ms),
not below it. 07.1-PERF-03-PROFILE.md section 5 projected a 25.00% gain from a fourth worker
(851.39ms to 638.54ms, the ideal-parallel floor), explicitly derived from linear-scaling
arithmetic (`1 - 3/4`) rather than a profiled figure -- that section's own text already flagged
this as "confirming that arithmetic," not new evidence. The measurement refutes the projection:
**this document corrects 07.1-PERF-03-PROFILE.md section 5 accordingly** (see that file's own
updated text). The reasoned explanation, stated as reasoning and not as a profiled mechanism: the
linear-scaling arithmetic assumes a fourth worker finds spare idle capacity, and a 4-core CI
runner running a headless browser harness (the browser main thread plus the Playwright-driven test
process both compete for the same four cores the sweep's workers also want) does not have that
spare capacity to give. Nothing in this plan profiled the contention directly; this is offered as
the most plausible account of why the arithmetic failed, not as a measured cause.

**Ground 2: the abort condition fired.** PERF-07b reached 76.9% of budget (12.30ms of 16ms
normalized) on this run, crossing D-20's 70%-of-budget escalation trigger the worker-count
adoption's own abort condition (PROJECT.md) was written against. Stated honestly: this is a single
sample, and the three width-3 runs already ranged 56.4% to 68.7% on the same statistic (9.03,
11.00, 10.14ms normalized against the 16ms budget), so 76.9% on its own, from one run, would be
thin evidence of a real regression rather than noise. **This ground is not load-bearing on its
own**: with no measured upside from Ground 1 to weigh it against, there is nothing width 4 buys
that would justify accepting even a modest, noisy risk to interactivity. It is not overstated here
as a proven regression; it is recorded as the second, corroborating reason the abort condition's
own text anticipated firing on.

**Action taken:** `workerCountForCores` reverted to `cores - 1` (floored at 1) in both
`src/sweep/sweep-pool.ts` and `bench/sweep-pool.ts`. `BASELINE_WORKER_COUNT` returns to 3,
`chunkCount` to 12. The correctness clamps this plan's own Task 1 acceptance criteria name
(`tests/sweep-pool.test.ts`, `tests/sweep/partition.test.ts`, `bench/sweep.bench.test.ts`'s
pool-versus-serial equality gates) were re-run at the restored width and pass, per section 5
above. `tests/sweep-pool.test.ts`'s own expectations were updated to assert width 3 (`4 -> 3`
worker count at 4 cores, `9 -> 8` at 9 cores), not left encoding the reverted-away width 4.
