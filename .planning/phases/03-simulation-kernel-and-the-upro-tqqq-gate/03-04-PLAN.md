    - Frequency `none` returns an empty schedule for any entry date and any window.
    - Frequency `daily` returns every bar index from 1 to `barCount - 1` inclusive, never index 0 (D-28).
    - Frequency `monthly` from an entry on 2015-01-17 returns the trading bars for 2015-02-17, 2015-03-17 and so on, one per month, and the count equals the number of whole months in the window.

    - A nominal date landing on a Saturday, a Sunday or a market holiday resolves to the next trading day present in the calendar; a nominal date that is itself a trading day resolves to itself (D-26).
    - Frequency `quarterly` steps 3 months per period and `yearly` steps 12, with the same clamp-then-roll rule.
    - A nominal date whose roll-forward would land past the window's last bar is not scheduled at all.
    - Two nominal dates resolving to the same trading bar throws an error naming both nominal dates and the shared bar; the returned indices are otherwise strictly ascending and duplicate-free.

Create `src/data/contribution-schedule.ts` exporting `ContributionFrequency` (the union
`'none' | 'daily' | 'monthly' | 'quarterly' | 'yearly'`, re-exported by `src/data/kernel-inputs.ts`
so `BacktestRequest` keeps its existing field type), `ContributionSchedule` (`{ barIndices:
Int32Array; nominalDates: readonly string[] }`, the second array kept for diagnostics and for the
script's printed header), `resolveContributionBars(calendar: Int32Array, entryCalendarIndex:
number, lastCalendarIndex: number, frequency: ContributionFrequency): ContributionSchedule`, and
`buildContributionFlags(barCount: number, schedule: ContributionSchedule): Uint8Array`.

`resolveContributionBars` works entirely in integer days-since-epoch, the same unit
`toDaysSinceEpoch` produces and the compiled calendar stores, so no rounding or floating-point
step exists anywhere in the path. Convert `calendar[entryCalendarIndex]` back to a UTC year,
month and day with `Date.UTC`-based arithmetic mirroring `toDaysSinceEpoch`'s construction. For
period `p` starting at 1, add `p * stepMonths` months to the entry's year and month (step 1 for
monthly, 3 for quarterly, 12 for yearly), clamp the day to `min(entryDayOfMonth,
lastDayOfTargetMonth)`, convert back to a day number, then binary-search the calendar slice
`[entryCalendarIndex + 1, lastCalendarIndex]` for the first index whose stored day number is
greater than or equal to that nominal day number. Stop when the search finds no such index. Emit
bar indices relative to `entryCalendarIndex`, so index 0 is always the entry bar and is never
present in the result.

Handle `daily` without any date arithmetic at all: bar indices 1 through
`lastCalendarIndex - entryCalendarIndex` inclusive.

After building the index list, assert it is strictly ascending; on a duplicate throw an error
naming both contributing nominal dates and the shared bar's ISO date. This is what makes the
`Uint8Array` flag representation sound: a flag can carry at most one contribution per bar, so a
collision must be an error rather than a silently dropped contribution.

`buildContributionFlags` allocates one `Uint8Array` of `barCount` and writes 1 at every scheduled
index. It allocates once, outside any per-bar loop the kernel will run, which is what keeps
SIM-11's contract intact.

Create `tests/data/contribution-schedule.test.ts` covering every behavior above against the real
committed calendar loaded through `loadBundleFromDisk`, plus a hand-built `Int32Array` calendar
for the collision case and for a synthetic long-closure case. Include an explicit case asserting
that a 2015-01-17 monthly entry produces exactly 12 contributions in the following 12 months and
that `totalContributed` from a run using that schedule equals `initialInvestment + amount * 12`,
which is the figure D-28 says a user will check by hand.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| CLI argv → `buildKernelInputs` | Operator-supplied leverage, dates, amounts and frequency cross into index arithmetic and schedule resolution |
| compiled calendar → schedule resolver | A binary-searched `Int32Array` drives which bars receive money |
| sourced constants → printed defaults | Cost parameters with varying confidence cross into a user-facing header |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-13 | Tampering (result integrity) | Contribution schedule resolution | high | mitigate | A duplicate resolved bar throws naming both nominal dates, so a `Uint8Array` flag can never silently swallow a second contribution; the ascending-and-unique property is asserted for every frequency |
| T-03-14 | Information disclosure | Binary search over the calendar slice | medium | mitigate | The search is bounded by `entryCalendarIndex + 1` and `lastCalendarIndex`, both derived from the already-validated run window, and returns no index when the target is past the end rather than clamping |
| T-03-15 | Tampering (result integrity) | Silent parameter coercion | high | mitigate | D-32: leverage outside the accepted band, an unknown frequency, an out-of-range entry date and an over-long holding period each throw naming the offending value and the supported range |
| T-03-16 | Repudiation | An unlabelled default read as a measured figure | medium | mitigate | The header labels every unspecified cost parameter as a default, names the constant, prints its confidence tag, and prints the spread's full range |
| T-03-SC | Tampering | npm/pip/cargo installs | low | accept | Zero new packages; 03-RESEARCH.md's Package Legitimacy Audit records the audit as not applicable |
</threat_model>
