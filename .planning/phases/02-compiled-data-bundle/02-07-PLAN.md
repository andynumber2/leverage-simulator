### Zero-row handling: a drop rule in the normalizer, not a calendar exception

`02-CONTEXT.md` leaves this to the planner. The decision is a drop rule in `normalizeNasdaq`, and `raw/calendar-exceptions.json` is not touched. Three reasons, in order of weight:

1. **A calendar exception would admit the zero rather than exclude it.** Under D-10 a bar on a date the reference calendar does not contain is fatal, and the reference calendar is derived from the longest daily equity series, which has no 2012-10-29 bar. Keeping the row and whitelisting the date under D-11 would therefore accept a 0.0 index level into the compiled Nasdaq-100 total-return series, and the kernel would read a minus one hundred percent return into it. The override file exists to accept a real vendor bar the calendar lacks, not to launder a fabricated one.
2. **D-03 puts per-source normalization in the fetch script.** A defect in one vendor's export is exactly the kind of vendor-specific concern that decision keeps out of the compiler. Routing it through the compiler's override file would put a Nasdaq export quirk into a file D-11 reserves for calendar facts a human accepted with a written reason.
3. **One rule covers all three defects in this export.** The placeholder row for today, the phantom Sandy row and the trailing all-empty line are all handled by dropping rows that carry no value, with no second mechanism.

The drop must not be silent. `normalizeNasdaq` returns both the rows and the dates it dropped, the run prints them, and `MAX_NASDAQ_ZERO_ROWS` is `5`: today's placeholder plus the one historical closure is two, and that count does not accumulate over time, so five is headroom for one or two further vendor closures without being loose enough to absorb a format change. Exceeding it throws naming the count and the dates, because a vendor that starts emitting zeros for real trading days is a data problem and not a parsing one.

### `normalizeNasdaq` contract

`normalizeNasdaq(csvText)` returns `NasdaqNormalizeResult`, carrying the canonical rows in ascending date order and the list of dropped dates.

Rules, in order:

1. Strip a leading byte order mark before anything else.
2. Split lines with the existing helper, which already normalizes carriage returns.
3. Require the header to match the expected five column names exactly, throwing and naming the header found otherwise. Locate the date and value columns by header name, not by position.
4. Split each data line with `splitCsvFields`, the quote-aware helper plan 02-06 added. A bare comma split mis-maps every column on a row whose index value carries a thousands separator, which is most of this file.
5. Drop a line whose every field is empty.
6. Parse the date as month, day and two-digit year. Resolve the century with a pivot at seventy: a year below seventy is in the two thousands, seventy or above is in the nineteen hundreds. This series begins in 1999 and cannot contain a year that pivot resolves wrongly. Emit the ISO form.
7. Strip thousands separators from the value before converting it, and require the result to be a finite number.
8. Drop a row whose value is exactly zero, recording its date. Throw when more than `MAX_NASDAQ_ZERO_ROWS` are dropped.
9. Reverse into ascending order, then assert strictly ascending with no duplicate date, throwing and naming the offending date otherwise. Do not sort: an unsorted input after reversal means the vendor changed its export order and that is a finding, not something to paper over.

### The standing cross-checks, measured during planning

Both were computed against the committed vendor files.

| Pair | First shared bar | Price value | Total-return value | Relative difference | Year-end ratio decreases | Final normalized ratio |
|---|---|---|---|---|---|---|
| S&P total return against S&P price | 1988-01-04 | 255.94000244140625 | 256.0199890136719 | 0.031252% | 0 across 39 year-ends | 2.2387 |
| Nasdaq-100 total return against Nasdaq-100 price | 1999-03-04 | 1933.030029296875 | 1933.03 | 0.000002% | 0 across 28 year-ends | 1.2209 |

The "year-end ratio" is the total-return value divided by the price value on the last shared bar of each calendar year, itself divided by that same quotient on the first shared bar, so it starts at exactly one and rises as dividends accumulate. Zero decreases across every year-end in both pairs is the divergence signature: a total-return series only ever pulls ahead of its price sibling, never back. A price series mislabelled as total return would sit on top of its sibling at every year-end and produce a final ratio of one, which is precisely what the previous vendor's data would have shown.

Assert on year ends rather than on every bar. Daily quotients wander by fractions of a basis point because the two indices round independently, so a strict day-over-day monotonicity assertion would be false for reasons that have nothing to do with the property being tested.

Assertion thresholds: first shared bar agrees within 0.1 percent relative for both pairs, zero year-end decreases in both, and a final normalized ratio above 1.10 in both. Every threshold sits well clear of the measured value in the direction that matters, and the ratio only grows with time.
