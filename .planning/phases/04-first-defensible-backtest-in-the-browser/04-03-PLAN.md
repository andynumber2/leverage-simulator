    RESEARCH.md's entire PERF-08 harness design rests on one unverified claim: that the `context`
    object a Vitest custom command receives exposes a real, unrestricted Playwright `BrowserContext`
    at `context.context`, supporting `newPage()` and, through it, `page.goto()` to an arbitrary URL.
    That claim is MEDIUM confidence, synthesized from documentation, and has no precedent in this
    repository. Settle it before building anything on top of it.

    Add a command named `probeBrowserContext` to the `bench` project's `commands` block in
    `vitest.config.ts`, declared in `bench/browser-commands.d.ts` alongside the existing seven. Its
    implementation inspects the received context and returns a JSON-serializable report with four
    booleans and one string: whether `context.context` is present; whether `typeof
    context.context.newPage` is `function`; whether `typeof context.context.browser` is `function`
    and calling it returns a non-null Browser (needed for a fresh-cache context in Task 2); whether a
    page opened from a freshly created context can navigate to `about:blank` and read
    `document.readyState`; and the constructor name of `context.context`. Wrap the whole body so a
    thrown error becomes a reported message rather than an unhandled rejection.

    Create `bench/playwright-context-probe.bench.test.ts` calling that command once and routing the
    report through `commands.recordInfoLine` under the id `playwright-context-probe`, so the answer
    lands in `.bench/bench-results.json`'s `infoLines` and survives the terminal scrolling. Assert
    that `newPage` is a function and that a fresh context can be created from the Browser handle.

    This file is not a throwaway: it stays committed as the standing regression that pins the
    mechanism, so a future Vitest or Playwright upgrade that removes the surface fails here with a
    named cause rather than inside a timing measurement.

    If the probe reports that `newPage` is unavailable or that no Browser handle can be reached, STOP
    and report rather than proceeding to Task 2. The documented fallback is a separate Playwright
    script invoked as its own npm run step, which costs Phase 1's D-03 one-measurement-pipeline
    discipline and is therefore a decision for the developer, not something to adopt silently.

    `dist` directory, asserts it exists and contains `index.html`, and throws a named error stating
    the missing path and the command that produces it when it does not, so a measurement can never
    silently run against nothing. It starts Vite's programmatic preview server over that directory on
    an ephemeral port, resolves the served origin, awaits `fn(origin)`, and closes the server in a
    `finally` so a throwing or interrupted measurement leaves no orphaned listener. It must serve the
    production build, never the dev server: the dev server ships unbundled ESM plus an HMR client and
    its cold-load timing has no relationship to what the static host serves.

    Add a command named `measureAppLoadTiming` to the `bench` project's `commands` block, declared in
    `bench/browser-commands.d.ts`. Its implementation, running Node-side and wrapped in
    `withPreviewServer`:

    Creates a genuinely fresh browser context from the Browser handle Task 1 proved reachable, so its
    HTTP cache is empty. Do not reuse the test runner's own context, whose cache is already warm from
    the run.

    Installs an init script before navigation that attaches a `PerformanceObserver` for the
    `longtask` entry type with `buffered: true`, forwarding each entry's duration to an exposed
    function that accumulates them Node-side.

    Navigates to the preview origin, waits for the `app-data-ready` mark to appear, reads its
    `startTime` from the page's own Performance timeline as the cold data-load-and-first-render
    figure, then waits for `app-interactive` and reads its `startTime` as the cold interactive
    figure. Read both from the page's timeline rather than the Node-side wall clock, so neither
    figure carries Playwright's own navigation-command overhead.

    Navigates a second time in the same context, whose HTTP cache is now warm, and reads
    `app-interactive`'s `startTime` from that second load as the warm figure.

    Closes the page and the fresh context, and returns a JSON-serializable object carrying the three
    figures, the maximum long-task duration observed during the cold load, the count of long tasks,
    and `navigator.hardwareConcurrency` as read in the page.
