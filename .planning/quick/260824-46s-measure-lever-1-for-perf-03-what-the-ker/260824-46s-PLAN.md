   `runBacktest`'s returned `KernelResult` scalars feed the per-cell metrics and that the per-bar
   arrays are write-only scratch the worker never reads back. Verified. Do not re-verify.

2. **The four readback sites inside the kernel, and their substitutions.** `src/kernel/backtest.ts`
   reads `outValue` back in the running-drawdown update at four places. Each needs a scalar
   substitution in the variant:
   - Lines 98 to 103, the `i === 0` cost-free anchor (D-03): reads `outValue[0]`. Substitute
     `initialInvestment`.
   - Lines 118 to 123, the already-ruined branch: reads `outValue[i]`, which that branch has just
     written as exactly 0 (D-22/D-23). Substitute the literal `0`.
   - Lines 152 to 157, the ruin-crossing branch: reads `outValue[i]`, likewise exactly 0.
     Substitute the literal `0`.
   - Lines 173 to 178, the ordinary path: reads `outValue[i]`, which was just assigned `value`.
     Substitute `value`.
   Line 181's `finalValue` also reads `outValue[barCount - 1]`. The `value` scalar already equals
   that array element on every path (it is `initialInvestment` at bar 0, exactly 0 after ruin, and
   the post-contribution value otherwise), so `finalValue` becomes `barCount > 0 ? value :
   initialInvestment`. Getting any of these five wrong changes `maxDrawdown` or `finalValue`, both
   displayed metrics, which is why Task 1's proof runs before Task 2's clock.

3. **The eight per-bar array writes to remove**, and nothing else: lines 95, 96, 97 (bar 0), 109
   and 112 (the long-gap flag, whose `longGapBarCount++` accumulator STAYS), 116 and 117 (ruined

   `droppedContributionsTotal`, `totalContributed`, `peakValue`, `maxDrawdown`, `ruined` and
   `ruinBarIndex` are all scalars already and stay exactly as written.

4. **Real-series delivery into the bench browser context already exists.**
   `commands.readKernelSeries()` (registered at `vitest.config.ts` line 130, implemented by
   `bench/kernel-series-bridge.ts`) returns a `ProductionKernelSeriesPayload`: plain `number[]`
   arrays for `returns`, `shortRate` and `calendarDaysElapsed`, plus `leverage` (3),
   `initialInvestment` (10000), `contributionAmount` (100), `financingSpread` (0.005),
   `expenseRatio` (0.0095), `longGapMinDays`, `seriesId` and `barCount`. It is SPX price-return
   from entry `1927-12-30`, the full committed history. `contributionFlags` is NOT in the payload;
   `bench/kernel.bench.test.ts` builds an all-zero `Uint8Array(payload.barCount)`. Rebuild the
   typed-array views once, outside every timed region, exactly as that file does.

5. **Precedent for proof-before-timing in a bench file:** `bench/canvas-repaint.bench.test.ts`.
   Its equivalence tests run and pass before either arm's `measureBatchedMinOfN` call, and its
   header states that an arm cannot win the comparison by painting less. Same structure here, with
   one addition: an explicit file-scoped guard, not just declaration order.

6. **Precedent for a diagnostic-only bench arm:** `bench/sweep-pool-profile.bench.test.ts` records
   exclusively through `commands.recordInfoLine` and never through the gated measurement-row
   channel, and declares its own standing cost budget. Copy that discipline. Recording a
   `MeasurementRow` here would require a budget id that does not exist and would trip
   `assertRunInvariants`'s unknown-budget-id check.

7. **A single-file bench run still persists its output.** `bench/global-setup.ts` writes
   `.bench/bench-results.json` (including `infoLines`) and prints the table BEFORE calling
   `assertRunInvariants`, which then sets `process.exitCode = 1` and rethrows. Running only this
   plan's file will therefore exit 1 on the PERF-08 coverage invariant while still printing and
   persisting every figure. **That exit code is expected and is not a failure of this measurement.**
   Judge the tests themselves from Vitest's own per-file summary, not from the process exit code.

8. **Harness primitives to reuse, never reimplement** (`bench/calibration.ts`): `REPEAT_COUNT` is
   5, `MIN_MEASUREMENT_MS` is 10, `measureBatchedMinOfN(n, batchSize, fn)` runs `fn` `batchSize`
   times per timed unit, `n` times over, enforces the 10ms floor against the batch total, and
   returns a per-call figure; `normalize(rawMs, score)` applies the D-06 calibration;
   `resolveRunCalibration()` (`bench/canonical-calibration.ts`) yields the run's one shared score;
   `captureEnvironment(score)` plus `commands.recordEnvironment` records the host block.

9. **The measurement host is not the D-17 baseline.** This sandbox reports 9 logical cores
   (`nproc`); the D-17 baseline is GitHub Actions `ubuntu-latest` at `hardwareConcurrency=4`, a
   different CPU under CI contention. Absolute milliseconds measured here do not port. The ratio is
   the deliverable for exactly that reason.

10. **The projection arithmetic FINDINGS must use.** `07.1-PERF-03-PROFILE.md` section 2 measured
    the zero-contribution branch at `hardwareConcurrency=4` as 72.2% kernel compute
    (`idealParallelFullGridMs = 851.39ms`) and 27.8% overhead-and-residual (`328.31ms`) of the
    gated run's measured raw `1179.70ms`. A kernel-time ratio `r` therefore projects to
    `851.39 * r + 328.31` ms raw on that reference run, not to `1179.70 * r`. For reference: even
    against the BEST of the five failing runs (1120.86ms normalized), closing to under 1000ms needs
    roughly 120ms out of the 851.39ms kernel share, so `r` must be below about 0.86; against the
    worst (1411.05ms) no value of `r` at or above 0 reaches 1000ms.

11. **Bit-identical comparison.** Vitest's `toBe` uses `Object.is`, which distinguishes `-0` from
    `0` and treats `NaN` as equal to `NaN`. Per-field `toBe` is the correct assertion here.
    `toEqual` on the whole object is not, because it does not distinguish signed zero.

12. **Bench project glob** is `bench/**/*.bench.test.ts` (`vitest.config.ts` line 78). The variant
    module must NOT carry a `.bench.test.ts` suffix. `tsconfig.json` includes `bench/**/*.ts` with
    `strict` and `noUncheckedIndexedAccess`, so `npm run typecheck` covers both new files.
